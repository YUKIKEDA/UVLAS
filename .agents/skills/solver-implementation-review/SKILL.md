# ソルバー実装レビュー

採用仕様に合うことと、仕様自体が妥当であることを区別する。実装者の説明・CI・過去の採用判定はレビュー入力であり、そのまま保証にはしない。レビュー依頼の範囲を守り、修正実装が依頼されていなければ本体を書き換えない。

## レビューする

1. 対象差分／版、ユーザー確定要件、採用仕様と追加規約の優先関係、対象パッケージ、主張する完了範囲を取得する。仕様自身に矛盾があれば実装欠陥と分けて記録する。
2. 対象コードから、元残差、未知量、時刻・履歴、必要微分、実際の返却／消費表現を再構成する。重要経路は仕様の式へ対応付ける。関数名の一致だけで適合としない。
3. 変更の影響が大きい数値境界を[数値レビュー観点](references/numerical-review.md)から選ぶ。全チェックリストを無関係な変更へ機械的に適用しない。
4. 試験の参照独立性、入力・閾値・観測の同一性、負対照、原系残差、格子／時間／精度感度を[証拠の審査](references/evidence-and-findings.md)で確認する。主コードで期待値も再生成するtestだけでは不十分な場合を特定する。
5. 疑わしい箇所は最小の再現・既存の独立fixture・方向微分／随伴・精度変更で調べる。必要な確認を実行できなければ、未確認範囲と合否への影響を明記する。
6. 実害を持つ指摘を優先度順で返す。該当箇所、発生条件、破る規約、影響、根拠、必要な修正／再検証を示す。推測だけの重大指摘や、好みのリファクタリングで埋めない。

## 合否の扱い

実装の適合、数値認定、実験妥当性、製品規模の性能、実務受入を別に判定する。重大な数値・状態不整合が残る場合は対象gateを保留する。要求の緩和や未達の正常化を修正案にしない。

不確かさを含む合否式と各閾値は対象プロジェクトから取得する。全案件に1%やBDF2、特定ライブラリを強制しない。既知の仕様を改善する必要があれば、変更の根拠と既存証拠の影響を明記する。

## 証拠hashの補助検査

`scripts/check_evidence_manifest.py`はローカルJSONの`source/artifact`参照をhash照合する**整合性専用**ツール。対応schema、使い方、制限は[証拠の審査](references/evidence-and-findings.md)を読む。科学的な合否・要求被覆・実行再現を自動判定しない。過去の`passed=false`がそのまま保持されても整合性は通り得る。

レビューの結論は、どの版・処理・条件まで確認したかを伴わせる。指摘なしの場合も、実行した検査と重要な未確認を短く添える。
