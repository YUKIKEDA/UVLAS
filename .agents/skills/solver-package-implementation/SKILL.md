# ソルバー実装パッケージ

成果は、採用仕様の決定に一つずつ対応した製品コードと、その決定を独立に確かめる試験、そして主張する完了状態を裏付ける記録。動くコードがあることだけを完了としない。

## 始める前

1. 対象パッケージの開始条件、依存パッケージの完了gate、止める位置（残リスク）を読む。入口条件を満たしていなければ、実装せずに不足を報告する。
2. 実装する決定をIDで列挙する。各決定について、式、時刻、単位、配列の形と成分順、所有権、失敗時の保証を仕様から書き出す。[決定から試験まで](references/decision-to-test.md)の表を使う。
3. 仕様に、実装者が方程式・未知量・時刻・返却値を選び直さなければ進めない穴があれば、その部分は実装しない。穴を仕様欠陥として報告し、残りを進める。
4. 研究試作に同じ処理があるか探す。あれば、何をそのまま移し、何を移さないかを決める。[試作から製品へ](references/porting-from-prototypes.md)を読む。

## 実装する

- 型と失敗の契約を先に書き、次に最小の正常経路、次に負対照の順で進める。
- 一つの決定を一つのPRに収まる大きさへ切る。後続パッケージの具体kernelを先走って足さない。
- 元系と元残差を保持する。縮約、投影、近似を入れるなら、元問題との同値性か、誤差と適用域を示す。示せない変更を最適化と呼ばない。
- 高精度の内部値を、消費側が受け取れない表現へ黙って丸めない。未対応の経路は拒否にする。
- 失敗した試行が親の確定状態、cache、世代を変えないことを、コードの形で保証する（親は読取り専用で受け、所有する候補を返す）。

## 確かめる

- 各決定に、独立な参照による試験を付ける。主コードで期待値を再生成する試験だけにしない。
- 許容差は仕様から取り、試験に数値と出典を書く。結果を見て緩めない。
- 負対照を正常系と同じ数だけ用意する気持ちで置く：空、ゼロ、非有限、特異、世代不一致、予算不足、未対応精度。失敗の種類が区別されることを確かめる。
- 局所で通った性質を、接続後・支持後の全体系でも確かめる。
- 試験が欠陥を検出することを、変異を入れて確かめる。
- 対象の全プラットフォームでクリーンビルドから通す。

## 報告する

完了の主張は状態を分けて書く：実装が仕様に適合、数値認定、実験妥当性、製品規模の性能、実務受入。このパッケージが主張するものだけを書き、主張しないものを明記する。

- 実装した決定IDと、対応する試験。
- 走らせたコマンド、版、結果。失敗と未確認もそのまま書く。
- 仕様からの逸脱と、見つけた仕様欠陥。
- 次のgateへ渡す条件と、止める位置にある残リスクの現状。

数値閾値、要素、言語、時間法、依存ライブラリは対象プロジェクトの採用仕様から取る。このskillは特定の方式を強制しない。
