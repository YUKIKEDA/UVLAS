# 再開・配布仕様

版：0.1、2026-10-29。Q25 A・Q26 Aにより必須範囲を確定。以下は実装・受入試験の設計案であり、再開機能や配布物の完成を示さない。

## 1. 確定した要求

- RUN-01：過渡解析を保存した途中の確定状態から再開する。
- RUN-02：フラッタ速度探索を完了済み条件と探索状態から再開する。
- DIST-02：ソース、Windows/LinuxのCLIバイナリ、Python wheelを提供する。

CLIとPythonは同じ計算コアと再開経路を利用する。可視化ファイルを再開データの代わりにせず、再開に必要な履歴をStateの設計時点から列挙する。

2026-10-30追記：[非線形ステップ契約](../structure/main-shell/q9-dynamics/nonlinear-step-restart-contract.md) と [構造単独の限定試験](../structure/main-shell/q9-dynamics/records/q9-nonlinear-restart-experiment.md) を追加。69自由度、非ゼロ初期ひずみの同じモデルで、受理前の状態分離、保存・再開一致、刻み変更時の再構築、不正データ拒否を具体化した。製造解の時間精度は成立したが、自然応答の時間収束は未達。RUN-01全体、後流・連成、CLI/Python相互再開、永続形式・OS互換性の合格ではない。

一般化α法の [候補比較](../structure/main-shell/q9-dynamics/records/q9-integrator-candidate-comparison.md) で算法加速度の保存も限定検証。位置・速度が一致していても算法加速度を端点物理加速度で再生成すると別軌道となった。方式ごとの版付き履歴を保存し、中点則の最小保存集合を一般化α法へ流用しない。

[保持荷重解放の契約](../coupled/j1/load-release-initialization-contract.md) では、準備荷重ID・解放時刻・左右の有効荷重集合・解放済みフラグ・方式初期履歴を保存対象に追加した。[限定試験](../structure/main-shell/q9-dynamics/records/q9-load-release-experiment.md) は初期イベント状態のJSON往復を確認した。任意の積分途中イベントや、後流を含むイベント再開の完成とはしない。

構造単独の既知時刻イベントは [境界・確定契約](../structure/main-shell/q9-dynamics/transient-event-transaction-contract.md) と [途中解放試験](../structure/main-shell/q9-dynamics/records/q9-event-transaction-experiment.md) で限定検証した。直前・境界左・境界右・境界後の再開、イベント未適用／適用済みと方式履歴、確定世代・出力カーソルの整合を確認。任意イベント・連成後流・実ファイル出力の障害復旧は未完了。

[UVLM時刻・データ契約](../aero/wake-loads/uvlm-discrete-time-contract.md) では、付着境界と物質点の別ID、後流面の循環・放出区間、束縛循環の過去値と実刻み、方式によっては循環微分履歴も保存対象とした。[空力側限定試験](../aero/wake-loads/records/uvlm-time-topology-experiment.md) で可変刻み・循環二時刻・指定移流の後流をJSON往復した。循環・後流を含む製品再開、コア・遠方閉鎖・全連成状態の互換性保証ではない。

## 2. 過渡解析の保存対象

| 分類 | 保存する情報 |
|---|---|
| 識別・互換性 | チェックポイント形式版、ソルバー版、モデル・解決済み設定の識別とハッシュ、単位・座標・配列型・配置、整合性検査情報 |
| モデル | 構造・空力の接続と参照形状、材料・断面・層、支持・剛体結合・集中質量・慣性、自由度対応、写像の物質座標。別ファイルに置くモデルは対応ファイルと検証情報を固定 |
| 進行状態 | 最終確定時刻、確定ステップ番号、刻みと必要な刻み履歴、初期化済み状態、励振・指定運動の時刻基準 |
| 構造 | 一般化座標・速度・加速度、採用積分法の内部履歴、拘束・反力等の再開に必要な状態 |
| 空力 | 束縛循環、循環差分の履歴、全揚力面の後流座標・循環・接続・放出時刻等、採用移流法の履歴 |
| 入力履歴 | 外力・突風・指定運動の参照データと識別、補間・イベント等の継続に必要な状態 |
| 出力の継続 | 実行ID、継続元、最終確定フレーム番号・時刻、診断と結果の継続位置 |

要素・積分法・後流方式の追加時は保存契約も更新する。ポインタ、プロセス内アドレス、作業用バッファを永続IDにしない。再計算できる分解・一時配列・キャッシュは保存必須にせず、再構築時間とメモリを測定する。

## 3. 保存と停止の単位

保存の基本単位は、構造・循環・後流・履歴を一度だけ確定した受理ステップ。Newton反復や連成反復の未収束状態は通常の再開点にしない。指定間隔の保存と、正常な停止要求に対する確定境界での保存を設計する。

保存中は以前の正常なチェックポイントを失わない。一時ファイル等へ書込み、整合性を確認してから新しい再開点として公開する方式を選ぶ。置換・同期・障害時の扱いは対応OSと実際のファイルシステムで試験し、未検証の原子性を保証しない。

強制終了では最後に書込みが完了したチェックポイントから再開する。保存後から終了までの計算は再実行し得る。書込み失敗は診断と終了状態に反映し、保存できたふりをして続行しない。

## 4. フラッタ速度探索の保存対象

完了した風速・荷重条件、平衡状態と残差・収束情報、モード／部分空間と対応、追跡分岐、既知の安定・不安定区間、未実行条件・追加探索キュー、臨界値の精度要求と停止条件を保存する。

未完了の固有値計算等は、再開後にその条件の開始点から再実行してよい。固有値ソルバー内部の反復を機種間でそのまま再開することは初期必須にしない。完了済み条件の脱落、同じ試行の二重確定、別モードへの無検知の切替を防ぐ。

## 5. 読込みと互換性

読込みは必要データ、チェックサム、形式版、モデル・設定の整合を確認し、モデルと状態を構築してから継続する。破損・欠落・未対応版・不一致を、部分読込みした正常状態として返さない。

初期の検証基準は同一ソルバー版・同じ数値方式と設定での再開。OS間の可搬性、版更新をまたぐ再開、変更を許す設定は、形式と配布対象を決めた時点で試験範囲を明示する。無条件の版間・機種間互換性は約束しない。

出力先や終了時刻等の変更を許す場合は、物理・数値モデルを変えない項目として明示的に列挙する。時間履歴やフラッタの停止条件を黙って変えた再開を同一計算と扱わない。

## 6. 再開の受入試験案

| ID | 試験 | 受入条件 |
|---|---|---|
| RST-01 | 非ゼロ循環・複数後流と構造運動を含む計算を複数位置で保存・再開 | 同じ受理時刻、構造・循環・後流状態と出力が再開専用許容差内で一致。許容差は事前設定し、製品の5%を流用しない |
| RST-02 | 励振変化・出力間隔・積分履歴の境界付近で再開 | 入力時刻・補間が一致し、循環履歴の欠落、後流の二重放出、出力の重複がない |
| RST-03 | 連成未収束・試行棄却後に最後の正常点から再開 | 試行履歴が混入せず、最後の確定状態・後流列数が保たれる |
| RST-04 | 書込み中断、切詰め、破損、容量不足 | 不完全ファイルを拒否し、以前の正常点を識別できる |
| RST-05 | 別モデル、設定不一致、未対応形式版 | 計算前に原因付きで拒否する |
| RST-06 | 粗走査・臨界近傍の追加探索中に停止・再開 | 探索点・分岐・モード対応が保たれ、連続探索の臨界値・精度条件と整合する |
| RST-07 | CLIで保存しPythonで再開、およびその逆 | 同じ保存契約を使い、対象状態と結果が整合する |

浮動小数点のビット一致は自動的に要求しない。後流列数・ID・時刻・履歴長・探索タスクの整合は別に確認する。臨界付近の成長率が不確かさの範囲で符号を変える場合は、安定性を断定せず評価精度を確認する。

## 7. 配布物と受入確認

| 配布物 | 含める内容 | 受入確認 |
|---|---|---|
| ソース | コア・CLI・Pythonバインディングのソース、ビルド定義、生成手順、依存情報、試験・小ケース、利用手順、ライセンス・通知 | 対応するクリーン環境から再構築して必須試験を実行 |
| Windows CLI | 実行ファイル、必要な実行時依存、利用手順、小ケース、ライセンス・通知 | コンパイラや開発ツリーを必要としない環境へ配置して実行 |
| Linux CLI | 実行ファイル、必要な実行時依存または要件、利用手順、小ケース、ライセンス・通知 | 宣言したLinux環境・CPUで、開発環境のパスやライブラリに依存せず実行 |
| Python wheel | 同じ計算コアを利用する拡張・Pythonパッケージ、必要な実行時依存、ライセンス・通知 | 対応Pythonの新規環境で、コンパイラなしに導入し構築・実行・結果取得・再開を確認 |

CLIとwheelで数値ロジックを二重実装しない。バージョン、設定、モデル識別、診断・終了状態を比較できるようにする。対応Python版、CPUアーキテクチャ、OS・ランタイムの最低条件、配布先はビルド試作後に具体化する。

第三者データは利用条件を確認したものだけを同梱する。原データの再配布条件が満たせないものは、出典・取得手順・加工手順を提供する。

## 8. 配布の受入試験案

- PKG-01：開発ツリーに依存しないソースビルド、依存版、生成ファイル・同梱ファイルを検査する。
- PKG-02：両OSのCLIをコンパイラのない対象環境で実行し、小ケースの入力→計算→診断→出力を確認する。`--version`だけで配布検証を完了としない。
- PKG-03：対象Pythonごとにwheelを新規環境へ導入し、モデル構築・実行・結果取得と異常入力を確認する。
- PKG-04：開発ビルド・CLI配布物・wheelで同じケースを比較し、規定した数値許容差と出力定義が一致することを確認する。
- PKG-05：各配布物で再開を実行し、形式互換性の宣言と実際の対応を照合する。
- PKG-06：同梱ライブラリ、実行時依存、ライセンス・通知、対応環境、ファイル一覧とチェックサムを確認する。

ビルド用コンパイラ・CMake・conda環境が動作したことと、利用者向けバイナリの配布互換性が成立したことを区別する。現在の隔離ツールチェーンからできた実行ファイルを、そのまま配布合格とは扱わない。

## 9. 着手時点で反映する設計

再開に必要な構造積分履歴・循環履歴・後流・入力状態はT09/T10からStateに持たせ、確定単位はT12で整合させる。Pythonバインディングを試す時点でwheelと実行時依存の収集も試作する。最終的なファイル形式と配布ツールは、これらの契約を満たす候補を比較して選定する。
