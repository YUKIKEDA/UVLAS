# Case から指定するチェックポイントの復元契約

[FD-08](case-schema-fields.md#fd-08-初期状態と再開要求) の `Restart.directory` は、ファイル Case ではその Case の親ディレクトリ、Python 辞書 Case では明示された `reference_root` から解決する。
[IO4-06](io-execution-adoption-specification.md#io4-06-checkpoint) の七つの互換性指紋は、保存側と復元側が実行に使う準備済み入力から、それぞれ同じ規則で導出する。
[チェックポイント容器](checkpoint-manifest-contract.md) の形式と、[J1 の確定状態・探索状態](../coupled/coupled-state-search-contract.md) に必要な履歴を継承する。

## Case 取得時に開いた根から復元先を選ぶ

ファイル Case はマニフェストを取得した `ReferenceInput` の読み取り根を使う。
辞書 Case の `reference_root` は同じ型の根として保持する。
`Restart.directory` を使う際に、根が指定されていない辞書 Case は `InvalidInput` を返す。
入力の取得後に作業ディレクトリを変えても、解決の起点は取得時に開いた根にとどまる。
schema の検査はディレクトリを開かない。
独立した `uvlas resume checkpoint-dir` に渡すホスト側パスは、本書の Case 内の相対規則の適用外である。

Case の宣言は[外部参照のパス正規化](reference-snapshot-start-contract.md#パスと実体)に従う。
区切りは `/` と `\` を認め、空の途中成分と `.` を除き、根の内側での `..` は対応する成分を消す。
絶対パス、ドライブ相対パス、UNC、ストリーム指定、根を越える `..`、末尾の区切り、正規化後に成分がない宣言を拒否する。
最後の成分は容器契約にある `checkpoint-<番号>` とする。
復元はこの番号だけを選び、親ディレクトリを列挙して別の確定番号を探す処理は行わない。

正規化後は、Case の保持する根のハンドルから、最後の成分までディレクトリとして開く。
Linux では `openat2` にディレクトリ指定と `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` を渡す。
Windows では親ハンドルを起点に一成分ずつ開き、reparse point を拒否する。
Windows の途中ディレクトリは、次の成分を開く間、削除・改名を共有しないハンドルで保持する。
最終ハンドルで `manifest.json` と全チャンクを検査し、検査したディレクトリをパス名で開き直さない。
別の根での再試行や、リンクを追う処理への切替は行わない。

AlmaLinux 8.10 の `4.18.0-553.189.1.el8_10.x86_64` は `openat2` をバックポートしている。
このビルドの外部参照取得と ext4 上の既存チェックポイント読み取りは検証済みである。
新しい Case 相対のディレクトリ取得は、同じカーネルでディレクトリ指定と根外・リンクの拒否を別途確かめる。
`openat2` または必要な解決フラグを提供しない Linux では、Case の相対復元を `Unsupported` とする。
ホスト側で選ぶ既存の読み取り経路の対応範囲は、その経路の契約と検証に従う。
[旧カーネルの外部参照取得と失敗注入](../../verification/IM-06/alma-8-kernel-runtime.md)・[ext4 での保存と読戻し](../../verification/IM-06/alma-8-checkpoint-ext4.md)

パス上限には元の UTF-8 バイト数、正規化後のバイト数、成分数を持たせる。
パスの変換と途中ハンドルの保持に必要な一時領域は、既存の読み取り上限と同じ `ResourcePlan` で確保前に照合する。
失敗の操作は `Recover` とする。
宣言の不備や根の未指定には `InvalidInput`、指定先の欠落、リンク、型違い、マニフェストやチャンクの破損には `CheckpointCorrupt` を返す。
安全な相対ディレクトリ取得を提供できない実行環境では `Unsupported` とする。
予算超過は `ResourceExceeded`、取消は `Cancelled` を優先し、途中結果を公開しない。
診断は可能な範囲で宣言の `/restart/directory` と不成立の箇所を示す。

## 実行に使う七つの入力群から指紋を求める

準備済み入力を、次の七群に分ける。
値は、型検査、単位変換、既定値の解決、物理準備を終え、実行に渡す値とする。
関係する処理が無効な場合はその区分を記録し、有効な処理の入力を欠いたまま指紋を作らない。

| 群 | ハッシュに含める入力 |
|---|---|
| `model` | 解析種別、単位変換済みの物理位置と幾何・トポロジー、離散化の物理 ID、空力面と物理後縁の所有、モデルに作用する荷重と既知入力の値・補間係数・イベント時刻。外部入力は消費する準備済み内容を結び付ける |
| `basis` | 参照基底の方式と準備済みの表現、物理 ID に対応する自由度と列順、基底の条件付けまたは座標移送に使う係数 |
| `material` | 材料と層の ID・順序・対応、密度・剛性・粘性、材料軸、初期ひずみと実行が使う層別パラメータ |
| `constraint` | 支持・接続から作った有効方程式、採用した行と自由度の順、固定ピボット・拘束チャートの対応、指定運動を表す準備済み係数・イベント |
| `algorithm` | 時間積分と区間・境界の再始動規則、輸送と後流の末端政策、解法・求積・探索と数値判定に使う実行設定。演算や受理判定そのものを変える上限を含む |
| `precision` | 各値群を保持・消費・射影する表現、精密化と投影の方針・予算、残差・比較に使う尺度と成分順 |
| `version` | 容器の schema、実状態のコーデック、準備済み入力の互換契約の版。コンパイラ・OS・ソース来歴は別に保存し、同一環境のビット一致の判定条件に使う |

入力の JSON キーの並び、ファイルの所在地、Case の元バイト列の SHA-256、`Restart` 宣言、保存先、消費されない説明・出所は来歴または入出力設定として保持する。
これらの値を互換性指紋の入力から除く。
同じ準備済み入力を使う保存と復元には、同じ七指紋が得られる。これにより、保存したマニフェストの SHA-256 を後から Case に書ける。
継続中の時刻、残りの予算、イベント位置と状態の各値はチェックポイントの実状態として保存し、その整合性を復元時に検査する。

### バイト列は群名・版・長さで区切る

各群を独立に SHA-256 でハッシュする。
`frame(x)` は、バイト数を表すリトルエンディアンの符号なし64ビット整数と `x` の連結である。
先頭に ASCII の `uvlas.checkpoint.fingerprint`、群名を順に `frame` で書く。
続けて、その群のバイト形式の版とレコード件数を、個別のリトルエンディアン符号なし64ビット整数で書く。
各レコードは `frame(ASCII のキー)` と `frame(値の正規バイト列)` からなる。
キーの順は ASCII バイトの昇順とし、同じキーの重複を拒否する。

本書で定めるのは七群への割当と共通のバイト形式である。
値の順序、整数幅、精度、単位、配列軸、区分は、準備済み型を定める側が、その型とともに版付きのフィールド表で固定する。
保存と復元をつなぐ前に、使用する型についてこの表が揃っていることを確認する。
配列は形状を先に記し、最後の軸が最も速く変化する順に並べる。
順序に意味のある ID 列は実際の消費順を使う。
順序に意味のない表には、型の ID 順または固定されたキー順を使う。
数値はリトルエンディアンとし、符号付き64ビット整数は二の補数、binary64 は IEEE 754 の64ビット表現を使う。
Binary64 の符号付きゼロは実行側が保持するビットを使う。
TwoWord は高語、低語の順で取り込み、どちらも保持する。
有理数を消費する型は、既約分数の符号付き分子と正の分母を十進 ASCII で表し、先頭の余分なゼロを除いて、それぞれ `frame` で区切る。
欠損と有効な空配列は、版付きの区分によって識別する。
構造体のメモリ配置やアドレスはバイト列に使わない。

フィールドの意味、順序、型、単位、含める値の集合を変える際は、影響する群の版を更新する。
削除・追加・区分の変更も同じ規則で扱う。
保存側の指紋は準備済み入力から計算し、復元側は現在の準備済み入力から計算する。
呼出し側が任意に選んだ指紋や、読み込んだマニフェストの指紋を比較の期待値に使う入口は設けない。
互換版と七指紋の完全一致を照合し、異なる場合は `CheckpointIncompatible` を返す。
異環境で数値を比較する試験も、復元時の照合には同じ七指紋を使う。環境によって準備済み入力が異なる場合は、どの値が異なるかを調べ、照合を省いて比較しない。
ハッシュは固定した順序で逐次計算できる。
バイト数・要素数・計算量を検査してから取り込み、準備入力の全複製を作ることを要件としない。

### 検査した容器から実状態を構成する

Case の `Restart.manifest_sha256` を、同じハンドルから取得したマニフェストの原本に対して照合する。
続けて schema、七指紋、全チャンクの宣言と内容を検査する。
検証済みチャンクから保存時の数値環境記録を読み、`Restart.compatibility` の環境条件を照合する。その後、受理済み物理状態と履歴を構成する前に J1 の ID・時刻・親子関係・ステンシル・荷重を検査する。
現在の準備済み入力、元の Case、最後の確定状態は読取り専用とし、成功時に新しい所有状態を返す。

数値環境記録は保存する実状態の版付きチャンク表に含める。保存時の実行側から取得し、マニフェストがそのチャンクのバイトを SHA-256 で照合できるようにする。復元先の記録は現在の実行側から別に取得する。
[QA-06 のビルド来歴](../../quality/quality-plan.md#qa-06-来歴) と [QA-07 の環境認定](../../quality/quality-plan.md#qa-07-環境の認定) に従い、実行版・ソース版と未コミット状態、OS・アーキテクチャ、コンパイラとその版、構成と数値演算に関わるビルド設定、命令セット水準、依存とランタイムの版を保持する。実際の丸め、非正規数の扱い、演算順に影響する並列実行条件も、実効値を記録する。記録は七つの互換性指紋とは別に照合する。未コミットの実行コードを含む場合、コミットと未コミット状態だけではソース内容の一致は確定できない。

| `Restart.compatibility` | 環境と観測予算の判定 |
| --- | --- |
| `same_environment_bitwise` | 保存時と復元先の数値環境記録を同じ版のフィールド表で比較し、全項目の一致を求める。同じ `platform_key` でもビルド設定やランタイムが違えば拒否する。比較に必要な実行来歴を確定できない場合も拒否する。`Restart.budget` は空とし、次状態と次荷重を同一環境の連続実行とビット単位で照合する。 |
| `qualified_cross_environment` | 保存元、復元先の順に数値環境記録を照合し、同じ七指紋と下記の観測計画・予算を対象とする V-STATE の認定記録を使う。保存元と復元先を逆にした実測は別の環境対の認定とする。 |

異環境の復元には、実行側が保持する製品の認定済み記録から該当する [V-STATE](../../requirements/practical-acceptance-plan.md#a5-02-部品部分系の必須入力と参照) の一件を選ぶ。認定記録は保存元・復元先、七指紋、観測の定義と対象範囲、認定した予算と比較結果、検証証拠の識別と SHA-256 を結び付ける。チェックポイントや利用者が渡した比較結果、QA-07 の各環境単独の認定、配布物の導入試験では代用できない。
`Restart.budget` は `Case.observations` の宣言順に一対一で対応させ、準備時に各観測 ID を付ける。認定記録とは ID、成分順・単位、物理対象・基底、時刻範囲・統計・片側、および SI にそろえた成分別の絶対・相対予算、尺度、誤差群の割当と予算の一致を確認する。復元位置と後続の観測が認定範囲に入ることと、記録した比較結果が全成分でその予算を満たすことを求める。

型と長さが正しくても、環境の不一致、該当する認定の欠落・重複、認定範囲外、観測または予算の不一致は `Recover / CheckpointIncompatible` とし、診断は `/restart/compatibility` または該当する `/restart/budget` の要素を示す。別の互換性モードへ切り替えない。必須チャンクの欠落やダイジェスト不一致は、容器契約に従って `CheckpointCorrupt` を返す。

J1 のチャンク割当には、IM-04 の受理済み状態で使う形状、成分順、ID、浮動小数点表現、時刻と状態の整合検査が必要である。
探索の再開には IM-05 の完了点、枝・モード対応、未処理キュー、再試行と資源残の所有状態を加える。
実状態の各フィールドとチャンク名・形状・保持精度を一対一で追える表を、対応する型と同じ実装単位で用意する。
この表と環境記録の版付きフィールド表、実状態の検査器が揃った時点で、利用入口を含む保存・復元の検証を始める。

## 両入口と消費する入力の差を独立に検証する

| 対象 | 参照と判定 |
|---|---|
| ファイルと辞書 | 正しい根と現在の作業ディレクトリに同名の異なるチェックポイントを置く。ファイルと同じ根を与えた辞書は正しい番号と同じチャンクを返す。根を省略した辞書、根外、絶対、リンクを拒否する。取得後に根のパス名が別の実体を指しても、新しい根を使わない |
| Linux のディレクトリ取得 | Ubuntu と既存の AlmaLinux 検証環境で、同じ読み取り根からディレクトリを開く。正常な確定名を選び、根外とリンクを拒否する。`ENOSYS` を注入した場合は `Unsupported` を返す |
| 宣言と容器 | 空白1バイトだけ異なる実マニフェスト、七群の指紋違い、欠落や余分なチャンク、資源上限を独立に作る。宣言 SHA-256 が違うときは JSON 読取り・チャンク取得の前に拒否する |
| バイト列 | 群 `model`、版1、キー `flow` の値 `00 80`、キー `geometry` の値 `41 42 43` を与える。独立の Python `struct.pack('<Q', ...)` と `hashlib.sha256` で導出した値 `5669a92d1e620f269743067b62554d040ce4551865dc797b18648c3d277ce2f7` と32バイトすべてを照合する。この例は外側のフレームを検査する |
| 指紋の入力 | 同じ準備済み入力を指す Case のキー順・配置・`Restart` 宣言を変更し、七指紋すべての一致を検査する。各群で少なくとも一つ、実際に消費する値だけを変え、対応する照合が失敗することを確認する。消費する外部入力の変更、列の入替え、TwoWord の低語のみの変更、版変更も含める |
| 復元する環境 | マニフェストの原本照合と七指紋が変わらないチェックポイントを使う。`same_environment_bitwise` では同じ数値環境から読み、復元先のランタイムの版だけを変えると `CheckpointIncompatible` になることを確認する。`qualified_cross_environment` では環境対と観測予算が認定記録に一致する復元を使い、記録の欠落、対の逆向き、対象外の再開時刻、観測の並びまたは成分予算だけを変えた場合を拒否する。いずれの拒否でも最後の確定状態を保つ |
| 実状態 | [V-STATE](../../requirements/practical-acceptance-plan.md) に従い、同じ J1 ケースの連続計算と再開を比較する。同一環境の次状態と次荷重はビット一致、別環境では別途定めた観測予算内とする。正しく再ハッシュした欠落・余分な履歴、BDF1 差替え、別親、偽の荷重を拒否し、元の確定状態を保つ |

既存の容器と Case の原本照合は[先行検証](../../verification/IM-06/case-checkpoint-manifest-digest.md)で確認した。
本書のバイト列例、相対解決と七指紋の受入条件は、後続実装でそれぞれ実行する。
