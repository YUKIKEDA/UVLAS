# 結果変更記録

基準結果（`qa/baselines/`）を変える変更は、同じPRに、ここへ記録を足す（[QA-04](../quality-plan.md)）。記録なしに基準結果を更新する手段はない：`tools/qa/results.py accept --record NNNN` が、記録の存在と、記録がそのケースを名指ししていることを確かめる。

ファイル名は `NNNN-<slug>.md`、番号は0001から。記録は書き換えない。訂正は新しい記録で行う。

二つの版の間で結果を変えた変更は、その間に足された記録の一覧である。リリースノートは、それを全て列挙する。

## 様式

```markdown
# NNNN: 何が変わったか、一文で

- Date: YYYY-MM-DD
- Issue: #N
- Pull request: #N
- 原因の分類: 不具合の修正 ｜ 算法の変更 ｜ 精度の扱い ｜ 依存の更新 ｜ コンパイラ・フラグ・命令セット ｜ 入力の解釈
- 仕様のID: N4-06, …
- 承認: （所有者の名前と日付。承認の前はmergeしない）

## 原因

何を変え、なぜ結果が変わるのか。推測ではなく、確かめたこと。

## 影響

| ケース | プラットフォーム | 量 | 変更前 | 変更後 | 相対変化 |
|---|---|---|---|---|---|

`results.py check` の出力を貼る。量ごとの相対変化の最大を書く。

## 数値予算との比較

受入精度の全数値予算（合力1%、ねじれ0.05°、固有振動数0.4%、フラッタ速度1%など）に対して、この変化が占める割合。予算を超えるなら、MAJORの変更である（QA-05）。

## 出荷した版への影響

既に出荷した版の結果が誤っていたのか（正誤が要る）、同じ精度の中の違いなのか。影響する能力とケース。

## 確かめたこと

変更の前後を、どのcommit、どのプラットフォームで走らせたか。変更が他のケースに及ばないことを、どう確かめたか。
```

記録は、まだ一つも無い。最初の基準結果（`numeric-canary`、2026-11-11、`windows-x64-msvc19.51-sse2`）は、新しいケースの最初の認定であり、変更ではない。
