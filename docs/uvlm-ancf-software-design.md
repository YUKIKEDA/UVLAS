# UVLM–ANCFシェル連成OSS ソフトウェア設計・実装計画

版：0.1（提案）  
作成日：2026年10月27日  
対象：UVLMとANCFシェルを単独・連成で実行できる解析プログラム

本書は初期の提案資料。現在の製品範囲は [製品要求仕様](product-requirements.md)、作業順と実装開始条件は [実装前設計計画](preimplementation-plan.md) を優先する。本書の擬似APIや方式候補は確定仕様ではない。

## 1. 本書の目的

本書は、UVLM–ANCFシェル連成OSSを「どのようなプログラムとして、どの順番で実装するか」に主軸を置く。用途の精度保証、実験計画、OSS運営は別の開発・検証・運営計画で詳細化し、本書では実装との接点だけを扱う。

記載する構成・型名・API・ディレクトリは初期提案であり、実装済みの仕様ではない。疑似コードは言語中立とする。実装言語、数値ライブラリ、ANCF要素、積分法、ファイル形式は未決定である。特定のライブラリの現行機能や性能を前提にしない。

最初の目標は、**小さな入力ケースをCLIで読み、計算し、履歴と格子を出力できるライブラリ中心のプログラム**とする。最終構成を先にすべて作るより、動作する経路を少しずつ伸ばす。

## 2. 設計の基本方針

1. 空力・構造・写像・連成を、それぞれ単独で呼び出せるようにする。
2. 変更されないモデル、時間で変わる状態、再利用する作業領域、出力用の結果を分ける。
3. 数式に近い逐次基準実装を先に作り、測定後に高速化する。
4. 関数の入出力、単位、座標系、時刻、配列配置を明示する。
5. 成功・未収束・入力不正を区別し、失敗を通常結果に混ぜない。
6. 検証ケースをCLIと同じ計算経路で実行できるようにする。
7. 初期段階では共通化を必要な箇所に限定し、汎用マルチフィジックス基盤やプラグイン基盤を先行開発しない。

## 3. 実装言語と依存関係の選定

### 3.1 判断項目

言語は既存コードの有無、開発者の習熟、線形代数・疎行列・固有値計算、配布、デバッグ、Python連携、対応環境で決める。C++、Rustなどの名前だけで性能や開発効率を判断しない。

候補ごとに、小さな技術試作で次を確認する。

- 密行列の組立・分解・複数右辺の解法。
- 疎行列の組立・分解、非線形反復での更新。
- CPUプロファイリング、メモリ検査、デバッガの使いやすさ。
- Windowsを含む想定環境でのクリーンビルドと配布。
- 必要ならC ABI経由のPython／.NET呼出し。
- 依存ライブラリとバイナリ配布物のライセンス。

初期はコア実装を一つの言語にまとめることを推奨する。Python等はケース生成・集計・図表に使い、製品計算ロジックを二重実装しない。ただし独立した小規模参照計算をテスト用に置くことはできる。

### 3.2 外部依存の境界

線形代数、ファイル読書き、並列化、可視化出力の依存を限定された層へ置く。公開APIに依存ライブラリ固有型を露出するかは明示的に判断する。すべてを独自ラッパーで隠すことは求めず、交換が必要な境界だけを薄く包む。

採用版とビルド条件を固定し、依存更新時は数値結果と性能の変化を確認する。

## 4. モジュール構成と依存方向

| モジュール | 責任 | 主な依存 |
|---|---|---|
| core | ID、座標・時刻の規約、診断・エラー、基本型 | 最小限の標準機能 |
| numerics | 線形解法、疎行列、反復支援、求積 | core、数値ライブラリ |
| geometry | 翼・シェルのトポロジー、幾何評価・品質検査 | core |
| aero | 誘導速度、循環、後流、空力荷重 | core、numerics、geometry |
| structure | ANCF要素、材料、拘束、組立、構造解法 | core、numerics、geometry |
| transfer | 空力点の埋込み、運動写像、一般化荷重 | core、geometry、構造表面評価API |
| coupling | 時間進行、連成反復、確定・再試行 | aero、structure、transfer |
| io | ケース、出力、チェックポイント | モデル・状態の公開読出しAPI |
| app | CLI、設定解決、実行、終了コード | 各公開API |
| validation | ケース実行、参照比較、報告 | appまたは公開API |

空力はANCF要素の内部を知らず、構造は渦や後流の内部を知らない。連成ドライバーが両者を組み合わせる。transferが利用する構造表面評価の契約は、小さなインターフェースとして定義する。

ioからコアを呼ぶ向きにし、要素・誘導速度関数からファイル出力やCLIへ依存させない。熱伝導など未知の将来機能のための抽象化は初期対象に含めない。

## 5. モデル・状態・作業領域・結果

### 5.1 データの分離

| 種別 | 例 | 寿命・変更 |
|---|---|---|
| Model | 接続、参照形状、材料、DOF対応、写像の物質座標 | 構築後は原則不変 |
| Settings | 刻み、許容差、後流方式、出力間隔 | 実行開始時に解決・記録 |
| State | q、速度、循環、後流座標、時刻、積分履歴 | 時刻・反復で変化 |
| Workspace | 行列、分解、残差、要素一時配列 | 容量を再利用 |
| StepReport | 収束、反復数、残差、診断 | 各試行の成否 |
| ResultFrame | 出力用荷重・変位・格子のスナップショット | 書出しまで不変 |

例：変形後の空力格子はModelの参照形状を書き換えず、Stateまたは評価キャッシュに置く。現在の積分法に必要な履歴を、後から出力ファイルから復元する設計にはしない。

### 5.2 疑似データ型

```text
AeroModel {
    surface_topology, reference_geometry, trailing_edge_topology,
    circulation_convention, force_evaluation_rule
}
AeroState {
    time, bound_circulation, wake_state, circulation_history
}
StructureModel {
    reference_nodes, elements, materials, dof_map, constraints
}
StructureState {
    time, q, velocity, acceleration, integrator_history,
    constraint_state
}
TransferModel {
    aerodynamic_point_ids, structural_element_ids,
    material_coordinates, offset_rules
}
CoupledState {
    time, step_index, aero_state, structure_state
}
```

要素ごとに自由度が異なる将来拡張はDOF対応表で扱い、初期から全自由度を節点6自由度へ押し込まない。ANCFの勾配成分は回転角ではない。

### 5.3 型と単位

NodeId、PanelId、ElementId、DofId等を区別し、異なる配列への誤インデックスを防ぐ。内部はSIと慣性系を基準にする提案とし、別座標を使う場合は型・関数名・引数で変換を明示する。

度／ラジアン、絶対位置／変位、力／一般化荷重、現在座標／参照座標を区別する。位置と勾配が混在する構造残差・収束判定には、自由度ごとの適切なスケールを用いる。無条件に同じノルムや単位を当てない。

## 6. メモリ配置とキャッシュ

### 6.1 初期配置

数値配列は連続領域を基本とし、行優先／列優先、成分順、所有者を文書化する。パネル・要素のID順を安定させ、ポインタを永続識別子にしない。

空力の影響係数行列は密、構造の組立行列は疎であることを初期の基本構成とする。逆行列を明示形成せず、分解して連立方程式を解く。小さな要素行列を大域の密行列として保持しない。

### 6.2 キャッシュの無効化

| キャッシュ | 再評価が必要な変更 |
|---|---|
| 空力パネル形状・法線 | 翼面位置・幾何規約 |
| 空力影響係数・分解 | 関連する相対幾何、コア、境界条件方式 |
| 構造疎パターン | 接続、DOF対応、拘束方式 |
| 構造接線の数値値 | 変形、材料状態、荷重の幾何依存 |
| 埋込みの接続情報 | 格子対応・トポロジー |
| 写像の数値ヤコビアン | 採用写像が依存する状態・時刻 |

数値配列と、どの幾何・設定世代から作られたかを結び付ける。変更のたびにすべて再計算する基準経路を残し、キャッシュ利用時との差を確認できるようにする。定常・剛体の条件で成立する再利用を、変形連成へ無条件に広げない。

### 6.3 後流

時間とともに増える後流を独立したデータ構造にする。放出列、循環、座標、後縁との接続、時刻履歴を管理する。初期は単純な連続配列、上限管理が必要になった段階でリングバッファ等を検討する。

保持長の変更・打切りは物理・数値モデルの変更として扱い、メモリ節約だけを理由に黙って適用しない。可変刻みでは列ごとの放出時刻・幾何から必要な情報を再現できるようにする。

## 7. API契約

公開APIは粗い実行単位にし、内部の小関数をすべて安定APIにしない。以下は役割を示す疑似APIであり、シグネチャは採用言語に合わせて確定する。

```text
build_case(resolved_input) -> ValidatedCase
initialize_aero(model, initial_conditions) -> AeroState
initialize_structure(model, initial_conditions) -> StructureState

evaluate_surface(structure_model, structure_state, point_bindings)
    -> positions, velocities, geometry_data

solve_aero_step(model, committed_state, trial_kinematics,
                time_context, workspace) -> TrialAeroResult

transfer_loads(mapping, trial_configuration, aero_loads)
    -> GeneralizedLoad

solve_structure_step(model, committed_state, load_evaluator,
                     time_context, workspace) -> TrialStructureResult

attempt_coupled_step(model, committed_state, step_settings, workspace)
    -> AcceptedTrial | StepFailure

commit(accepted_trial) -> CoupledState
```

各関数は、入力を変更するか、出力の所有権、参照の有効期間、座標系、評価時刻、作業領域の再利用可否を定める。荷重は現在の構成に依存するため、構造解法へ固定配列を渡すのか、評価関数を渡すのかを積分・連成方式と合わせて決める。

外部向けAPIと内部APIの安定性を分け、初期公開はCLI入力と少数の実行APIを優先する。

## 8. UVLMの実装分解

| 順番 | 機能 | その段階の動作確認 |
|---|---|---|
| A1 | 有限直線渦・渦輪の誘導速度 | 単独点・対称配置・符号 |
| A2 | 翼格子と幾何評価 | 接続、法線、面積、後縁 |
| A3 | 影響係数、右辺、定常循環 | 非貫通残差、対称翼 |
| A4 | 荷重と係数、作用点 | 合力、モーメント、単位 |
| A5 | 後流放出・指定移流 | 列数、接続、循環受渡し |
| A6 | 循環履歴・非定常荷重 | 指定運動の短時間応答 |
| A7 | 自由後流・高速化 | 基準経路との比較 |

空力荷重は合力だけでなく、作用点と力の組を取得できるようにする。連成用の空気力評価点と非貫通点を混同しない。非定常荷重の差分式が必要とする履歴と、始動時の処理を同じ場所で管理する。

## 9. ANCFシェルの実装分解

| 順番 | 機能 | その段階の動作確認 |
|---|---|---|
| S1 | 形状関数・導関数・参照配置 | 補間・幾何・積分 |
| S2 | 要素質量・弾性エネルギー・内力 | 剛体運動、微分との整合 |
| S3 | 接線・疎行列組立 | 差分方向微分、対称性の成立条件 |
| S4 | 拘束と静的非線形解法 | 片持ち小変形、荷重増分 |
| S5 | 時間積分と初期化 | 自由振動、刻み感度 |
| S6 | 表面位置・速度の評価 | 指定点、曲げ・ねじり |

要素カーネルは大域状態から必要な要素自由度を受け取り、要素内力・接線を返す。大域組立・境界条件・ファイル操作を要素カーネルへ入れない。

内力・接線の導出方法は手計算、記号生成、自動微分等から選ぶ。方法名だけで正しさを判断せず、エネルギーの方向微分、接線の方向微分など独立した数値確認を行う。差分確認では刻み幅依存と丸め誤差を調べる。

拘束は消去法と未定乗数法のどちらを初期採用するか決める。後者なら線形系の性質と適切な解法、前者なら反力の復元方法を定める。

## 10. 写像の実装

空力点に対して、対応構造要素と物質座標を前処理で作る。初期配置での探索結果を保存し、現在形状上の最近傍を毎ステップ選び直すことを標準動作にしない。

位置写像をx=g(q,t)、ヤコビアンをJ=∂g/∂qとし、速度をJ qdot+∂g/∂t、一般化荷重をJᵀ fとして評価する。単純なANCF形状関数補間ではJを固定できる場合があり、法線オフセットなど非線形写像では状態依存となる。この違いを写像ごとに宣言する。

初期はJ全体を形成する分かりやすい経路を用意し、必要なら後からJv・Jᵀfを直接計算する方式にする。大域の巨大な密写像行列を常に保持する必要はない。

荷重伝達のテストでは、任意の許容仮想変位で仕事が一致するかを確認する。ANCF勾配へ通常の回転モーメントを直接足すAPIを設けない。

## 11. 連成の状態管理

### 11.1 確定と試行

```text
while not finished:
    committed = current_state
    dt = choose_step(committed)
    trial = attempt_step(committed, dt)

    if trial.accepted:
        current_state = commit(trial)
        publish_accepted_frame(current_state, trial.report)
    else:
        discard(trial)
        report_failed_attempt(trial.report)
        retry_with_smaller_step_or_stop()
```

committedは試行中に変更しない。最初は必要な状態のコピーで分かりやすく実装し、測定後に二重バッファや差分管理へ改善する。作業領域や分解キャッシュは更新可能でも、失敗した試行の履歴を次の試行へ混入させない。

### 11.2 強連成反復

同一時間ステップ内で構造予測→空力評価→荷重写像→構造更新を反復する。時刻nの状態から作る試行と、反復前回値を初期推定に使うことを区別する。構造ソルバーを呼ぶたびに時間を進めない。

後流の仮更新・放出は採用方式に従うが、確定する後流列と循環履歴は受理されたステップにつき一度だけ更新する。後流を反復内固定する近似を使うなら設定と結果に記録する。

可変刻みを導入する場合、循環差分、後流放出間隔、構造積分履歴のすべてが対応する必要がある。初期は固定刻みと、失敗時に確実に停止する動作から始め、刻み縮小再試行を別の開発項目にする。

### 11.3 構成依存荷重と接線

Newton法等で荷重の構成依存性を接線へ含めるか、固定点反復・近似接線で扱うかを明記する。近似方式でも収束試験と残差の評価を行い、接線を一部省いたことを隠さない。

## 12. 入力・出力・再開

### 12.1 入力処理

入力読込み→構文検査→単位・既定値の解決→意味検査→モデル構築の順に分ける。軽量な設定形式と格子・配列データを分離するかは規模を見て決める。最初に独自の複雑なバイナリ形式を設計しない。

最低限、schema_version、単位、形状、材料、拘束、流れ・運動、解法・刻み、出力設定を持つ。未知キー・重複指定・未対応機能は原則エラーとし、誤記を黙って既定値へ落とさない。解決後の全設定を保存する。

検査対象は、非有限値、負の厚さ・密度、接続範囲、退化要素、法線・後縁、拘束の不整合、無効な刻み・許容差を含む。物理的適用範囲の警告と、計算続行不能な入力不正を区別する。

### 12.2 出力

| 種別 | 内容 |
|---|---|
| 実行情報 | 版、コミット、入力ハッシュ、環境、解決済み設定 |
| 履歴 | 時刻、荷重、変位、エネルギー等の選択量 |
| 診断 | 残差、反復、刻み、失敗試行、警告 |
| 可視化 | 空力格子、後流、構造格子、選択した場 |
| 終了情報 | 成功、利用者停止、未収束、入力・I/Oエラー |

初期はテキスト履歴と標準的な格子出力を候補とする。大規模配列の圧縮・階層形式は測定後に選ぶ。途中停止時も完了時刻と最終確定状態を識別できるようにする。書出し失敗を正常終了にしない。

### 12.3 チェックポイント

q・速度・加速度だけでなく、積分履歴、拘束状態、循環履歴、後流、現在時刻・刻み履歴、モデル識別情報を保存する。再計算可能なキャッシュは保存を必須としない。

チェックポイント形式を版管理し、モデルと非互換な再開を拒否する。一時ファイルへの書出し後に置換する等、対応環境で整合したファイルを残す方式を選ぶ。可視化ファイルを再開用データの代替にしない。

## 13. エラー・ログ・診断

| 区分 | 例 | 処理 |
|---|---|---|
| 入力不正 | 無効ID、厚さ不正、非有限値 | 計算前に位置付きで拒否 |
| 幾何不正 | 退化、反転、写像不能 | 関連IDと状態を報告 |
| 数値失敗 | 特異系、反復未収束、非有限演算 | ステップ不受理または停止 |
| I/O失敗 | 出力不能、再開形式不一致 | 保存状況と終了状態を報告 |
| 内部不整合 | 配列長・接続の矛盾 | 開発者向け診断を残して停止 |

エラーに時刻、ステップ、反復、要素／パネルID、残差等を付ける。低レベル関数は必要な診断を返し、画面出力は上位でまとめる。毎パネルのログを通常実行で出さない。終了コードは分類し、自動実行で判定できるようにする。

| 部品 | 渦の符号、形状関数、求積、要素内力、接線 |
| 性質 | 対称性、剛体運動、仮想仕事、妥当な座標変換 |
| 結合 | DOF組立、荷重受渡し、後流接続、連成履歴 |
| 実行全体 | 入力→計算→出力→再開、終了コード |
| 数値検証 | 定常・非定常理論、格子・時間・後流収束 |
| 回帰 | 修正した不具合の最小ケース、過去の重要結果 |

初期から実装に意味のあるテストを付けるが、単純なアクセサや実装式のコピーを大量に作ることは優先しない。グラフの画像一致だけでなく、元数値を比較する。

連成の状態管理には、受理／棄却、反復回数を変えた後流列数、失敗後の再試行、連続実行と再開の一致を含める。非有限値や退化入力も小さなケースで確認する。

PRでは短時間の必須試験、定期実行では収束・長時間ケース、リリースでは対象範囲全体を実行する。デバッグ構成と最適化構成を確認し、採用言語で利用可能なメモリ・未定義動作検査を組み込む。

## 15. 性能改善の進め方

1. 小・中・大の固定ケースで総時間、工程別時間、ピークメモリを測る。
2. 行列組立、分解、誘導速度、後流、構造内力、連成反復、出力の寄与を分ける。
3. 余計な割当・コピー・再計算を減らす。
4. 条件が成立するキャッシュ・分解再利用を導入する。
5. ホットループの配列配置・ベクトル化を調整する。
6. CPU並列、近似高速化、GPU等を必要性に応じて追加する。

単なる行列解法のベンチマークだけで製品性能を評価しない。強連成反復数と後流増大が総時間へ与える影響も測る。密行列の記憶量、分解負荷、後流の直接相互作用は規模とともに急増するため、想定格子数・後流列数からメモリを見積もる。

外側の並列ループと線形代数ライブラリ内部の並列を同時に無制御で使わない。決定的な加算順が必要な経路と、高速経路の許容差を定める。fast-math等の浮動小数点最適化は数値差を評価して採否を決める。

## 16. 外部連携・GUIの境界

初期の利用経路はCLIとコアAPIを優先する。GUIはケース編集、実行、進捗、結果閲覧を担当し、数式・収束判定を持たない。長時間計算は別プロセス実行も候補とし、停止要求は確定境界など安全な位置で処理する。

Python／.NET等との連携を行う場合は、粗い単位のC ABIやバインディングを設ける。境界で、ハンドル寿命、配列所有者・形状・配置、解放関数、エラー、例外の扱いを決める。言語ランタイムの例外をABI境界の外へそのまま流さない。

外部呼出しが細粒度になり毎要素・毎渦線の往復が発生する構成を避ける。UIやバインディングが変わっても、同じケースをCLIで再現可能にする。

## 19. 初期段階で作り込まないもの

汎用プラグインABI、分散計算、GPU専用構成、独自線形代数、独自可視化エンジン、高度なGUI、汎用メッシュ生成器、全言語向けバインディングは初期必須にしない。必要性が分かった時点で設計を追加する。

一方、時刻の整合性、一般化荷重の定義、試行と確定の分離、診断、再現可能な入力は後付けの負担が大きいため、初期から確保する。
