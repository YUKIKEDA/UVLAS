# 保存済み結果の終了状態と来歴を照合する

既存の `status.json` と `provenance.json` から、過去の終了コード、失敗の詳細、最後の確定 ID、元ケースと解決済みケースの識別情報を読み戻す。状態文書に記録された SHA-256 を来歴の正確なバイト列と照合し、両方の検査が通った場合に結果を返す。[IO4-01・IO4-05](../../specs/foundation/io-execution-adoption-specification.md) [元の出力](result-documents.md)

## 状態と識別子の食い違いを検出する

既存の厳格な JSON 読取り器で、キーの重複や不正な UTF-8 を拒否する。状態、失敗、元ケース、ビルド来歴には、既存出力と同じ項目と型を要求する。完了フラグ、終了区分、失敗原因の組を確認する。最後の確定状態は、ID だけ判明している場合と、モデル世代・数値世代・SHA-256 も判明している場合を区別する。失敗にも確定 ID やモデル世代があれば、対応する確定状態と照合する。識別子の10進表記は uint64 として読み、最大値をそのまま保持する。

両文書のバイト数、深さ、要素数や文字列の上限には、既存パーサーへの指定を使う。資源計画はこの二つの読取りで共用し、取消を各読取り前後と返却前に確認する。出力は状態・出典とビルド来歴を所有し、入力の所有者と資源計画が破棄された後も読める。

## 書き出した結果と、改変した対照を読む

既存の書出し処理の全終了区分、失敗文脈、確定状態の所有情報を読み戻した。過去の別ビルドの情報もそのまま保持できた。来歴だけのバイト変更、JSON キーの重複、上限を超える ID、終了区分やモデル世代の矛盾は検査で拒否した。失敗の対照には、来歴のダイジェストを更新しても項目と値の検査で拒否される例を含む。

この入口が照合するのは状態と来歴の組である。解決済みケースの実バイトとの照合、ディレクトリからのファイル取得と CLI 表示は呼出し側が担う。記録にある確定状態は報告用の識別情報であり、ソルバーを再開する状態とは別に扱う。

Windows の MSVC 19.51.36260.0 Debug と Linux の GCC 14.2.0 Debug（ASan・UBSan）で、結果文書と解決済みケースの対象2件が通過した。結果文書では8ケース・409アサーションを確認した。Linux の clang-tidy 21.1.1 で本体と試験を検査した。
