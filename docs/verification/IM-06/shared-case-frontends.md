# CLI と Python でケース検査と結果確認を共有する

IO4-01・IO4-02・IO4-05。CLI の `validate` と Python の `load_case`、`case_from_dict` は、同じ C++ のスキーマ検査と外部参照取得を使う。Python は検査済み入力と参照を所有し、CLI と Python の結果確認は照合できた `status.json` の元バイト列を返す。

## 入力の同一性と失敗

ユニコードのファイル名、CRLF を含む入力と結果、参照 SHA-256 の不一致、未対応の参照役割、解決済みケースの改変を照合した。辞書から生成した入力は Python の `Decimal` で独立に組み立てた JSON と SHA-256 が一致し、元の辞書を変更しても保持された同一性は変わらなかった。循環、非有限値、不正な Unicode、非対応の型を拒否した。辞書の符号化では、深さ、文字列と数値のバイト数、ノード数、生成バイト数の上限も検査した。参照グラフの取得順、共有先の再読込み防止、循環と深さ上限は、[参照グラフの検証](reference-graph.md)に記録した。

瞬時観測の時刻窓に `[float(2**63), 2**63]` を与えた。以前の最短十進表記では、同じ時刻の両端を不一致として拒否した。binary64 を厳密な有限十進数に展開すると検査が通った。`10**700` を含むケースは、Python の整数文字列上限を 640 桁に変更しても、ファイルと辞書の両経路で `Nonfinite` を返した。

## 静的な点変位・支持レンチの参照

FD-09・V-USE。手入力、Gmsh MSH 4.1、Nastran BDF の3経路で、同じ矩形Caseと観測を使った。公開例の条件投影を独立Pythonで再計算し、参照レコードと成分の順序を反転した。CLIの `validate` とPythonの `load_case` が全経路を受理した。Python辞書のbinary64値は正確な十進字句を別に作ってハッシュへ入れた。ファイルの十進値と辞書の値が異なるときはファイル向けの参照を拒否し、辞書向けの参照を受理した。 [採用契約](../../specs/foundation/observation-reference-json-contract.md)

元バイト列を変更すると取得時のSHA-256検査で拒否した。元ファイルのSHA-256を更新しても、条件指紋、厚さ側、基底、時刻と時刻側、成分の欠落・重複、単位、不確かさ、支持IDと原点の不一致を拒否した。未対応版は `Unsupported` を返した。二つの参照ファイルを持つCaseでは、2件目の原点だけを変えるとCase内の2番目の宣言と参照側のノードを診断した。原点照合を外した隔離ビルドでは、3入力経路とも原点違いを誤って通し、回帰試験が失敗した。

C++試験では所有した親・参照元・条件の指紋と、解析値の変位 $1/512$ m、反力 $-4167633984375/4194304$ N、二つのモーメント $4167633984375/4194304$ N mを厳密に照合した。外部精度領域または作業量が2ファイル分より1だけ足りないとき、1件目を保持したまま2件目を拒否した。別の親と取消を拒否した後も、元の参照から値を取得できた。Ubuntu 24.04のGCC 14.2 Release、CPython 3.12.3で、`io.observation_file`、`python.case_file_operations`、`python.ownership` の3件が通過した。実状態からの観測と比較判定は載荷平衡の確定後に検証する。
