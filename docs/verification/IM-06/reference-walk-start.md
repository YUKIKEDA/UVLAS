# 先頭の根宣言から参照依存の走査を始める

IO4-01の参照解決で、検査済みの根宣言の先頭1件を取得し、元バイト列とdigestを照合した後に依存走査へ渡す。中間結果は、仮想根からの辺と処理中の頂点、元バイト列と宣言位置を保持する。この頂点は役割ごとの依存抽出を待つ。

## 取得順と所有権を照合した

- 八つの根宣言を含む実ファイル例で、先頭の参照ファイルだけを用意した。仮想根からの辺は1本、処理中の順序番号は0、完了した頂点は0件。マニフェストのSourceId 19、参照先のSourceId 300、役割 `gmsh-msh4.1-ascii`、宣言ポインタ `/model/geometry/0/mesh` を固定値と照合した。ファイルを削除し、入力、根、宣言表とPlanを破棄した後も、3バイトの `abc` と独立SHA-256を完全一致で確認した。
- 同じ親の参照ゼロでは、根も資源枠もなしで空の走査を得た。参照ゼロでも、呼出し側のSourceIdが異なる親、およびSourceIdが同じで元バイト列が異なる親を拒否した。

## 資源と最初の失敗を照合した

- 既知の根の固有source数と走査の初期化に必要な容量を取得前に検査した。8頂点、最大深さ1の例では初期化18単位、最初の辺1単位で走査開始に19単位を使う。初期化の作業量、Plan、取得全体のPlanは境界と1不足で確認した。子の依存宣言によって増える頂点の容量は、抽出器と結ぶ段階で扱う。
- 未取得ファイルと誤digestは、DFSの辺と深さの上限を同時に超える条件でも、取得の失敗として報告した。正しいdigestでは辺、作業量、深さの上限を個別に拒否した。診断予算がゼロの場合も拒否理由と宣言位置のnodeは保持した。取消と失敗から中間結果は返らず、同じ親を使った再試行に成功した。失敗までに成功した確保はPlanに残った。

## 検証環境と結果

ソース `9ff84c2deeb5088defc3e2f9a9f75e0ccf85c497`、Windows AMD64、MSVC 19.51.36260.0 Debug。ビルド情報の `uncommitted_changes` は `false`。対象CTestは2件が通過し、新規3ケースで132アサーションを確認した。隔離コピーで第2宣言を選ぶように変えると、そのファイルが存在しないため先頭取得の試験が終了コード42で失敗した。

対象のclang-tidyはWindowsとWSLで実行した。GCC 14によるLinux実行はPR CIで確認する。役割ごとの依存抽出、後続の根と子の取得、全参照の資源集計、所有する最終結果の公開はIM06-0の参照snapshot段階に残る。
