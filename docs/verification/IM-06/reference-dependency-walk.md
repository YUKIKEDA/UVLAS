# 参照依存を宣言順にたどる

IO4-01の参照依存を、仮想根と処理中の参照先から宣言順に受け取る。新しい参照先は明示スタックに積む。完了済みの参照先は共有する。完了順に追加できるのはスタックの先頭だけなので、依存先が依存元に先行する。

## 固定ケースと境界

- 凍結した [参照snapshot設計ケース](reference-snapshot-design-cases.json) のSourceId 10、20、30を内部の順序番号0、1、2に対応させた。巡回順は0、1、2、完了順は1、2、0、受理した辺は5本だった。共有された順序番号1は一度だけ完了した。
- 次の辺が処理中の頂点に戻るとき、宣言のsource、role、位置と、スタック上の循環区間に終点を加えた列を記録した。複数頂点の循環は0、2、0、自己参照は2、2。診断ごとのバイト数、ResourcePlanの残量、作業量のいずれかが不足する場合は、循環の分類と宣言の情報を保持した。診断の確保失敗でも同じ結果を得た。
- 頂点数を $N$、設定した最大深さを $D$ とすると、初期化の作業量は $2N + \min(D,N)$。受理した辺と頂点の完了は各1単位。循環列の保存には、閉じる辺の1単位に加え、列の要素数分の作業枠を要求する。失敗した操作は走査状態や走査の確定済み計数を変えない。
- 頂点、辺数、深さ、作業量、確保バイト数を境界と1不足で照合した。初期確保3か所の失敗、取消、仮想根とスタック先頭に反する呼出しを試した。2,048頂点の列は明示スタックで処理し、10,240単位で完了した。初期化後の成功経路では追加の確保を行わなかった。

## 検証環境と結果

ソース `62466fe78709bebf974a8b508851f405870066c9`、Windows AMD64、MSVC 19.51.36260.0 Debug。ビルド情報の `uncommitted_changes` は `false`。対象のCTest 2件が通過し、新規5ケースで6,297アサーションを確認した。順序番号0への循環判定を除外した隔離コピーはコンパイルとリンクに成功し、循環例の試験が失敗した。Catch2の終了コードは42だった。

clang-tidy 21.1.1をWindowsとWSLで実行した。GCC 14によるLinux実行はPR CIで確認する。役割ごとの依存抽出、参照取得と走査の統合、全参照の資源集計と公開結果はIM06-0の参照snapshot段階に残る。
