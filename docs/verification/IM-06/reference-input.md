# FileとMemoryの参照入力を検査済みケースへ結び付ける

IO4-01の参照取得のために、同じ元バイト列から作った `SchemaCase` と取得元を一緒に所有する内部入口を追加した。Fileは直上のディレクトリを根として開き、一成分の名前で取得したマニフェストハンドルを保持する。マニフェストの検査済みバイト列と文書の長さ・SHA-256を照合し、その文書をschema検査へ渡す。Memoryは呼出し側から開いた根を受け取る。外部参照がゼロなら根を省ける。

## 取得元と失敗時の動作を照合した

- 上位と直上に同名のマニフェストと別内容の参照ファイルを置いた。直上のマニフェストから作ったケースの元バイト列は8,611バイトで、Python 3.12の `hashlib.sha256` が凍結テストケースの連結文字列から求めた `ecfba5a3cdf129b195b7e1504c74c2981852f6ee57617ac320ea14420ffd9a38` と一致した。根から開いた参照ファイルは期待する3バイトと完全一致した。
- 元名とは別のハードリンクから取得した実体IDが、保持するマニフェストのIDと一致した。Fileの結果を移動して、移動元が無効になり、取得時のResourcePlanを破棄した後も照合に使えた。Windowsで、結果が生きている間は根とマニフェストの改名が拒否され、結果の破棄後に改名できた。
- 同じ元バイト列とSourceIdを与えたFileとMemoryで、ケース識別子が一致した。Memoryはマニフェストの実体IDを持たない。全8役割のケースでは、供給した根から期待する元バイト列を読み、根なしと移動済みの根を拒否した。参照ゼロのケースは根なしで取得できた。
- 不正な一成分名、欠落、不正なJSONとschema、ファイル長の上限、開始時の取消を検査した。FileとMemoryの各取得段階は同じResourcePlanへ計上する。schemaの失敗時予約を含む合算上限で成功し、1バイト不足では `ResourceExceeded` を返した。
- Fileの読取り領域は文書を作った時点で解放する。その後、schema検査が内容を所有する。ここで検査した予算は取得・文書・schemaの製品所有領域の累積計上であり、OSや外部ライブラリのピークメモリの測定値は含まない。

## Windowsでの検証結果

ソース `d48c15a29edc65fbb637e799ff0f12d924fff289`、Windows AMD64、MSVC 19.51.36260.0 Debug、補修済みnlohmann/json 3.12.0。ビルド情報の `uncommitted_changes` は `false`。

`ctest --test-dir out/issue215-build -C Debug -R '^io\.(reference_input|windows_reference_root)$' --output-on-failure` で対象2件が通過した。新しい試験の内訳は4ケース・138アサーション。作業ツリーと別の一時ディレクトリに置いたC++のコピーで、外部参照があるMemoryの根なし拒否を外した。コピーはコンパイルとリンクに成功し、対象試験の拒否アサーションで失敗した。Catch2の終了コードは42だった。対象のclang-tidy 21.1.1とclang-format 21.1.2も通過した。

Linux向けの試験は、根のパスを開いた後に移し、元の場所に別内容を置いてから同じ根をMemoryへ渡す。認定済みGCC 14での実行はPR CIで検証する。依存グラフ、roleごとの依存抽出と物理準備への接続はIM06-0の参照snapshot段階に残る。
