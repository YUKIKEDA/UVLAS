# チェックポイントマニフェストの検証

[マニフェストとチャンク集合の契約](../../specs/foundation/checkpoint-manifest-contract.md)を `io.checkpoint_manifest` で検証する。

- 手書きのマニフェストと、Pythonの `struct.pack` と `hashlib.sha256` で別に得た2チャンクの固定値を用いた。符号なし整数42とf64の1を指定の順序で復元し、入力バイト列を書き換えた後も値を読めることを確かめる。
- チャンク名の重複、パス成分、大文字、NUL、余剰キー、重複JSONキー、誤った長さ・型・形状・SHA-256、コンテキストの指紋違いを検査する。
- 2件目の破損と欠落・余剰・重複を拒否し、取消でも部分集合を返さないことを確認する。
- 同じチャンク集合の異なる入力順から同じ文書を生成し、出力上限とチャンク総量の1バイト不足を拒否する。

`io.checkpoint_directory` は型付きチャンクからマニフェストを生成して実ディレクトリへ保存し、指定番号と最新番号の読戻しを検証する。2桁と1桁の番号の順序、既存番号での保存拒否、破損または別モデルの新しい候補の除外、完成したデータを含む一時名からの拒否、候補上限を検査する。

Linux GCC 14 Releaseでは、構造・空力を含む合流先で対象12件が通過した。ソースの複製で最新候補の降順を昇順に変えると、2種類の候補拒否試験のどちらも、番号12と値47の代わりに番号4と値42を拾った。独立に固定した番号と値の計4アサーションで検出した。

Windows MSVCの合流先では、Debugのチェックポイント関連4件と、Releaseのチェックポイント・JSON読取り関連6件が通過した。確定時の一過性アクセス拒否を再現し、[保存側の有限再試行](checkpoint-publication.md)を入れた後、Releaseで確定保存と往復を各60回反復した。両OSで使った合流ソースは `a650b266c9e6e683884e91d70e581850cd7f5cca` に固定した。

レビューへの追試では、正しいチャンクと同居する未宣言の `chunk-extra.bin` を指定番号で拒否し、最新探索では前の番号を返すことを確認する。列挙件数の上限ちょうどと1件不足を比較し、Windowsの単一読取りバッファに収まらない件数でも検査する。Linuxでは祖先のリンクを経由した保存と復元をともに拒否し、実パスでの往復を照合する。
