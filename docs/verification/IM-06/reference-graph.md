# 照合済みファイルの参照グラフを所有する

マニフェストに直接書かれた参照を先に検査し、宣言順に深さ優先でたどる。初めて出会った参照は、固定した根を使って開く。開いた実体の重複、読み取り前後の長さと変更指標、元バイト列の SHA-256 を照合する。役割別の処理が子宣言を抽出する時点では、一時ハンドルを閉じている。処理中の参照への辺は循環として拒否し、完了済みの参照を再訪したときは元バイト列を共有する。共有先を含めてグラフの深さを検査する。[IO4-01 外部参照の契約](../../specs/foundation/reference-snapshot-start-contract.md)

成功結果は親の識別情報、元パスと正規化後のパス、元バイト列とダイジェスト、宣言位置、隣接表、依存先が先になる完了順を所有する。同じファイルへの宣言も出現ごとに残す。マニフェストの宣言位置は JSON のノード番号と Pointer、子の宣言位置は宣言元ファイルの SourceId とバイト位置で示す。消費側は親の識別情報を照合し、SourceId と役割を指定して取得済みの配列を借りる。

子を発見した時点で、頂点、辺、保持できるパスと作業量を検査する。動的に拡張する領域は、旧領域が生きている間に新領域を同じ資源計画へ計上する。ファイルの長さ、EOF確認を含む読み取り回数と容量、ハッシュ対象バイト数、実体の比較数は、単一ファイルとグラフ全体の両方で制限する。子の SourceId 照合は頂点表の比較回数も作業量に含める。途中の失敗で候補を破棄し、入力と根宣言は再試行に使える。

## 検証

[開始審査の固定例](reference-snapshot-design-cases.json) にある依存関係 A→B、A→C、C→B を、実ディレクトリ上のファイルに適用した。子宣言は試験の抽出器が供給する。最初の取得が A、B、C の順で、完了順が B、C、A になることを手書きの列と照合した。B と C は同じバイト列を持つ別実体とし、B を再取得せずに共有することを確認した。マニフェストの反復辺、明示された元パス、正規化後のパス、親と役割の照合を検査した。入力、資源計画、元ディレクトリを破棄した後も、子の元バイト列と独立に計算した SHA-256 が一致した。

C→A に変更すると、元の宣言位置に循環を返した。後続のマニフェスト参照が欠落していても、先行する子の SHA-256 不一致を先に検出した。同一実体のハードリンク、根外へ出るパス、固有 source 数と深さの上限も拒否を確認した。

Windows の MSVC 19.51.36260.0 Debug と Linux の GCC 14.2.0 Debug（ASan・UBSan）で、参照入力、パス、ファイル取得、根の準備、依存走査、Gmsh メッシュ、Nastran Bulk Data の対象7件がそれぞれ通過した。参照入力は各15ケースで、Windows は742、Linux は746アサーションが通過した。

Linux では clang-tidy 21.1.1 で変更した取得・走査・参照グラフと結線試験を検査した。取得済みの共有先を再度開く変更を隔離環境に入れると正常例が失敗し、元のコードへ戻すと43アサーションが通過した。

## 対応する形式と後続の完了条件

製品の役割別処理は、Gmsh MSH 4.1 ASCII の採用範囲と、対応カードを含む単一ファイルの Nastran Bulk Data を検査する。どちらも取得したバイト列から依存宣言がないことを確かめる。他の役割では実ファイルを照合した後、形式検査を提供できない場合に `Unsupported` を返す。[Gmshメッシュ入力契約](../../specs/foundation/gmsh-mesh-input-contract.md)・[Nastranデッキの検証](nastran-bulk-leaf-verification.md)

- Nastran と Gmsh の sidecar は、ケースの辞書と単位・IDの意味を共有する。ファイルのキー、ID間の対応、重複や競合の扱い、Nastran材料の不足する3D定数の指定を、各 importer 契約で固定する必要がある。Nastran の `INCLUDE` を扱う場合は、子のパスとともに、宣言済みの SourceId・役割・SHA-256 を得る方法も決める。[ケースのフィールド辞書](../../specs/foundation/case-schema-fields.md)
- 参照幾何、準備履歴と初期履歴、比較観測のファイルは、マニフェストに役割とダイジェストの欄がある。参照曲面と部材・境界の対応、履歴と受理済み状態の対応、観測列の単位・時刻・左右の対応は、それぞれファイルの形式と検査条件が必要になる。[ケースのフィールド辞書](../../specs/foundation/case-schema-fields.md)・[入出力・実行・再開の実装仕様](../../specs/foundation/io-execution-adoption-specification.md)
- 物理準備では、外部面を共通の参照幾何・厚さ・材料・拘束へ変換し、幾何誤差に加えて質量と仕事、変位と反力、対象固有値を確認する。対応する IM-01〜03 の物理準備、IM-04／05 の受理済み状態を使う再開、V-USE と V-STATE が IM-06 の終了条件に含まれる。[実装開始審査](../../plans/implementation-start-review.md)
- 配布では、REL-1 で対応下限・manylinuxタグ・署名・公開先を定め、REL-2 で配布物の作成と検査を自動化する。実際のCLIとwheelを新規環境へ導入し、同じケースの結果と失敗および再開を照合する。公開は全必須用途の実務受入の後に行う。[ランタイム検証](private-runtime-image.md)・[ロードマップ](../../roadmap.md)
