# Release の照合記録をリンク時の出力に結び付ける

Windows と Linux の Release ビルドで、更新時刻を保って別の拡張に置き換えると、照合記録の再生成が失敗することを確認した。
正規に再リンクした後は記録を再生成でき、CLI と拡張を移設した監査で所有権試験10件が両環境で通った。

## リンカーの出力をあとから照合する

CLI と Python 拡張のリンクがそれぞれ成功した時点で、実ファイルと Git リビジョンを示す生成ヘッダーの SHA-256 を記録する。
`uvlas_runtime_artifact_manifest` は両方を読み、現行のファイルやリビジョンが異なれば、以前の照合記録を残して終了する。
診断が出たらそのターゲットを再リンクし、[監査手順](runtime-artifact-producer-review.md)に従って記録を作る。
ビルドディレクトリとリンク時の記録は、操作者が管理していることを前提とする。

## 以前の更新時刻とリビジョンを使って対照した

修正前の Linux では、インポート可能な同名の拡張をコピーして更新時刻を元へ戻すと、Ninja は拡張を再リンクせず、旧ターゲットが差し替えたファイルを記録した。
修正後は両環境で同じ操作を拒否した。代替の拡張と、同じ SHA-256 を持つ旧リビジョンの模擬リンク記録を組み合わせても拒否した。
失敗前後にリンク時の記録と公開済みの照合記録を比較し、内容が変わらなかったことを確かめた。
最後に隔離ビルド内の拡張とリンク時の記録を除いて再ビルドし、両成果物が再び照合に通ることを確認した。

ビルドしたコミット、終了値、再生成した記録と通知のハッシュは[検証記録](im06-runtime-artifact-link-receipts.json)に記載した。
