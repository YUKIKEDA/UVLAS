# Ninja の依存データベースから入力文書のヘッダーを照合する

既存の Linux 一括監査で、CMake の Ninja と Unix Makefiles のどちらを使ったかをビルド先の CMakeCache から判定する。対象は製品の `input_document.cpp.o`。Ninja では `ninja -t deps` で `.ninja_deps` を読み取る。オブジェクトに対して有効と報告された単一のレコードを使う。問い合わせの前後でデータベースの SHA-256 を照合し、結果にその指紋を残す。[監査の入口](../../build.md#非公開のランタイム用ディレクトリ)

## 実際の Release ビルド

Ubuntu 24.04.5 の GCC 14.2、Ninja 1.11.1、CPython 3.12.3 で使った固定元は `3a140d7bfbffef797a3fb7b29187dc458e50f53a`。対象オブジェクトに個別の `.d` はなく、依存データベースに449件が有効な状態で残っていた。四ヘッダーと CLI・拡張の例外提供元が期待値に一致し、両入口で BDF・MSH と二つの対応表を持つ同じ Case を受理した。 [Case と元入力の指紋](im06-private-wheel-external-references.json)

## 拒否した対照

- 同じ固定ビルドに別の `stl_bvector.h` の指紋を期待値として渡すと、実際のヘッダーとの不一致を報告した。
- 別に複製したビルドで文書オブジェクトの更新時刻だけを変えると、Ninja は同じ記録を `STALE` と報告した。オブジェクト、CLI、拡張、生成記録、データベースのバイト列が元と同じ場合も、監査は古いレコードを拒否した。
- もう一つの複製では、GCC 14.2.0 原典の `stl_bvector.h` を Ninja で実際に読むようにし、対象オブジェクトを再コンパイルして CLI と拡張を再リンクした。ヘッダー日付 `20240908` と、対象オブジェクト、両製品、生成記録の SHA-256 は元と同じだった。新しい有効レコードが示したヘッダーの SHA-256 が期待値と異なり、監査は拒否した。

三つとも終了コード1で、成功 JSON は出力されなかった。監査ソース `eb88c6d882f52e5b45c57986fe5595d39d9d70a0` を固定し、Ninja と Unix Makefiles の両方でビルド領域を読み取り専用にして再実行した。AlmaLinux 8.10 の Unix Makefiles ビルドでは、元の `.o.d` を使う一括監査も通った。依存記録の指紋は固定したビルド領域の検証に使う。入力パーサーの本体受入と正式な配布範囲は各ゲートに残る。 [前段のGNU Make検証](linux-parser-input-qualification.md)
