# 保持した根から参照先の元バイト列を取得する

IO4-01の参照取得で、検査済みの親と宣言の初出順を照合し、その親が保持する根から選んだ一つの参照先を開く。最初のファイル情報を使って実体を判定する。許可されたファイルは同じハンドルから取得し、前後のファイル情報と宣言されたSHA-256を照合する。結果は元バイト列、検査済みdigest、実体ID、親と宣言位置を所有する。

## 実体の拒否と取得の順序を確かめた

- 制御した読取り器で、マニフェストの実体が先に判定されることを確認した。マニフェストに一致しない場合は既出ファイルの実体を比較する。実体照合で拒否した各例は、情報取得1回、読取り0回、バイト列のPlan確保0件だった。オブジェクトIDが同じでファイルシステムIDが異なる対照は別実体として許可した。
- Windowsの実ファイル試験では、Fileのマニフェストの元名とハードリンクを、誤digestかつ読取り予算ゼロでも `Cycle` とした。異なるSourceIdの同じ実体は `DuplicateFile` とし、同じ内容を持つ別実体は許可した。Memoryでは、別に作成したマニフェストのハードリンクを通常の参照ファイルとして受け取った。
- 元ファイルを消し、根、入力、Planを破棄しても結果を照合できた。独立したPython SHA-256に対して、3バイトの `abc` と、凍結ケースの8,611バイトを完全一致で確認した。診断には元の宣言位置を記録した。
- 実体比較回数と読取りバイト数の上限を境界と1不足で調べた。欠落、digest不一致、別親、不正な参照先の順序番号、取消を拒否することを確認した。診断用の文字列を保存できない場合も、元の分類を保持した。

## 検証環境と結果

ソース `21af74a394dcf44404ea21915e9b92fe73c4d1ac`、Windows AMD64、MSVC 19.51.36260.0 Debug。ビルド情報の `uncommitted_changes` は `false`。CTestで `io.reference_file_snapshot`、`io.reference_input`、`io.windows_reference_root` の3件が通過した。新規分は4ケースと110アサーション。マニフェストの実体比較を反転した隔離コピーは、コンパイルとリンクに成功した後、元名とハードリンクの両対照で失敗した。Catch2の終了コードは42だった。

clang-tidy 21.1.1はWindowsとWSLで確認した。GCC 14によるLinux実行の検証はPR CIで行う。役割ごとの依存抽出、依存順、全参照の資源集計、公開結果はIM06-0の参照snapshot段階に残る。
