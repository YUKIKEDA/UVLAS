# 参照先を開く前にマニフェストの宣言を索引化する

採用契約IO4-01の参照取得に向け、検査済みの宣言を元の順序のまま所有し、各宣言をSourceIdの初出順の参照先に対応付ける。繰り返しの宣言も元のパスとJSON Pointerを保持する。SourceIdが同じ場合に元のパス・SHA-256・役割が一致するという、既存schemaの保証を利用する。関連するファイルの実体の同一性は、後続の取得処理で確認する。

## 宣言順と資源の境界を確認した

- 独立に列挙した8役割・9宣言を、JSONのキー順を反転したケースと照合した。繰り返したSourceIdを一つの参照先に結び付けた後も、9件の出典を個別に取得できた。元パス、digest、役割をそれぞれ変えた再宣言は、既存schemaが拒否した。
- 8本の正規化パスと合計116バイトを照合した。異なるSourceIdの正規化済みパスが同じ例では両方を保持した。二つの不正パスでは、宣言順に最初の拒否箇所を報告した。JSON Pointerの容量が1バイト不足した場合は詳細のPointerだけを省き、同じ失敗分類を返した。
- 宣言数、辺数、固有source数、正規化後の合計バイト数と成分数、作業量、ResourcePlanの上限を、ちょうどと1不足で照合した。作業量は、宣言・索引の初期化、処理する宣言、各索引の探索、および各固有パスの原文バイト数の16倍を数える。この倍率は既存の正規化処理の走査とコピーを覆う上界である。基準ケースは手で数えた `9 + 9 + 19 + 9 + 11 + 16 × 128 = 2,105` 単位と一致した。
- 8つのパスと3つの表で実測した11確保点に、1点ずつ失敗を注入した。呼出し元の宣言はすべて保持された。最終確保中の取消でも結果は公開されなかった。参照宣言ゼロでは追加Plan確保0、作業量0だった。

## 検証環境と結果

ソース `8c39950563c9a3a9921bb5d38eb30bcd5cc16ae3`、Windows AMD64、MSVC 19.51.36260.0 Debug。ビルド情報の `uncommitted_changes` は `false`。対象の `io.reference_root_plan` と `io.reference_declarations_resources` がCTestで2/2件通過した。新規分の内訳は前者4ケース・149アサーション、後者1ケース・40アサーション。

隔離したソースコピーでは、1件のSourceIdの共有を外すと検証用のケースで固有source数が8から9に増え、宣言の対応順も変化した。コピーはコンパイルとリンクに成功し、順序と所有の試験がCatch2終了コード42で失敗した。

clang-format 21.1.2と、変更した翻訳単位のclang-tidy 21.1.1を確認した。Windowsの構成に加え、WSLでもLinuxの標準ライブラリを使って静的解析した。認定済みGCC 14での対象試験はPR CIで確認する。参照先の実体照合と読取り、roleごとの依存抽出、循環判定はIM06-0の参照snapshot段階に残る。
