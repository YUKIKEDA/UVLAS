# 前縁と後縁の対応を決める独立対照

[#390](https://github.com/YUKIKEDA/UVLAS/issues/390) の設計について、Python の有理数を使い、製品の格子生成を呼ばずに照合した。 [採用する対応と幾何の条件](../../../specs/aero/wing-edge-pairing-contract.md)・[検証コード](reference.py)

## 境界が同じでも照会点は変わる

平面で前縁を $(0,0)$ から $(0,5)$ m、後縁を $(1,0)$、$(1,1)$、$(4,5)$ m とする。後縁の線分の長さは1 mと5 mになる。翼幅中央・翼弦3/4の照会では、両縁で同じ翼幅位置を使うと $(51/32,5/2)$ m、各縁をそれぞれ弧長で正規化して明示対応に入力すると $(33/20,103/40)$ mとなる。差は $(9/160,3/40)$ m。上向き法線と鉛直流速 $U_z=y/(10\,\mathrm s)$ を使うと、法線流速に $3/400\,\mathrm{m/s}$ の差が出る。両方の対応で同じ外周を覆うことも照合した。

共通の $t$ 範囲が異なる平行四辺形では、明示対応があれば被覆を認定できる。明示欄の省略、後縁の端の逆接続、同じ後縁パラメータの二重指定をそれぞれ拒否した。明示節点の間に後縁の折れ点がある対照で、その折れ点の逆像 $\eta=1/2$ が分割に入ることを確認した。参照外周に切り欠きを足した対照は、閉区分の局所的な向きがすべて揃っても拒否した。各区分が厳密凸で同じ向きを持ちながら、離れた区分が重なる対照も拒否した。

## 凍結した二翼の六条件

凍結結果の SHA-256 は `72427831e87dd0a25f98ebccd2d0e3dac6f3bcbeb3ffa4c7181f6ba5a5b537bf`。結果の六条件を順に読み、モデルを定義する三つの元ソースもハッシュで確認した。元の翼平面式を使用し、後退と上反角の三角関数係数、テーパー、尾翼原点の0.6は凍結入力から移した binary64 値を厳密な二進有理数として保持した。元の翼平面式は翼ごとの物理翼幅から直接評価し、対照側は Case の chart、折れ線境界、Frame を別々に読み、前後縁の対応を通じて位置を計算した。 [凍結結果](../../../../rd/aero/multi-surface/records/multiple-surface-harmonic-refined-result.json)・[二翼を組み立てる元ソース](../../../../rd/aero/multi-surface/experiments/run_multiple_surface_harmonic.py)

主翼と尾翼を左右それぞれの半翼に分け、4つの `surface_graph` を使った。各翼の根では、明示した共有境界と正準化前の離散頂点の順が左右で一致した。主翼または尾翼の Geometry の参照だけを相手翼と交換した対照は、面IDと格子の形を保っていても、元面ごとの独立位置の比較に失敗した。

| 上反角 | 格子（各翼） | 渦頂点 | 非貫通点 | 後縁帯 |
| ---: | --- | ---: | ---: | ---: |
| 0°、5°の各条件 | M2/N8 | 60 | 32 | 16 |
| 0°、5°の各条件 | M4/N16 | 180 | 128 | 32 |
| 0°、5°の各条件 | M8/N32 | 612 | 512 | 64 |
| 計 | 6件 | 1,704 | 1,344 | 224 |

合計3,048点の位置が成分ごとに厳密一致した。後縁は渦頂点の最終列に含まれる。後縁帯の列は条件と面ごとの必要件数を照合した。正準 `EdgeId` の発行と転写符号、位相付き荷重の検証は製品準備と求解へ渡す。

## 再現

Python 3.12.3 で実行した。標準ライブラリのみを使う。最初のコマンドは六条件の Case と同じ幾何欄をメモリ上で再構成する。二つ目は、先行の `uvlas validate` で確認した6件の型付き Case ファイルの正規のバイト列を受け取り、[検証コード](reference.py)に固定したSHA-256を確認してから同じ独立位置比較を行う。両方で同じ件数を得た。

```bash
python3 -B docs/verification/IM-03/wing-edge-pairing/reference.py
python3 -B docs/verification/IM-03/wing-edge-pairing/reference.py --cases <typed-case-directory>
```

型付き Case を読む実行は通常と `-O` でバイト一致し、出力の SHA-256 は `f9408673ee6db03a5f661cfd08b2de0f02df137ce9fe86a5960f743aa6d3bdbc` だった。隔離した版で外周の完全一致を検査する箇所を外すと、`-O` でも切り欠きの対照が失敗した。
