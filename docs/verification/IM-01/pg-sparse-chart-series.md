# 実PG接続系列の固定ピボット準備計測

[固定ピボット疎チャート](../../specs/structure/pg-sparse-chart-contract.md)の準備を、実PGのパッチ数と接続数を変えて測った。対象はR-02の容量調査。実務規模の形状や時系列については[A5-06の性能受入](../../requirements/practical-acceptance-plan.md)で確認する。

## 入力と固定条件

平板の単位正方形 A、B、C、D を、世界座標の `(0,0)`、`(1,0)`、`(0,1)`、`(1,1)` に置いた。回転は単位行列、基準長さは1 m。厚さは全片で1 m、層境界は $\zeta=-1,-1/3,1$。物理パッチIDは順に17、72、45、89。分割の $n$ は順に1、2、1、1。Aの左辺を全厚、右辺零で固定した。

| パッチ | 接続（物理ID） | 隣接グラフ |
|---|---|---|
| A、B | AB (118) | 1辺 |
| A、B、C | AB (118)、AC (315) | 2辺の木 |
| A、B、C、D | AB (118)、AC (315)、CD (406)、BD (507) | 4辺の閉路 |

いずれもPG辞書、積分分割、参照幾何、ランク、厳密平板Gram、条件付け、PreparedPatchの順に各パッチを準備した。全厚トレースは独立に得た両側の外部辺列を入力した。各片で物理辺の始点、終点、被覆を検査し、各標本に辺区間の列が一致しない接続を含めた。式、全厚、支持の優先と物理IDは全標本で固定した。

製品の `ResourcePlan` は一実行48 GiB。大域集約は4パッチ、5拘束、4,096原行、150,000非零を上限とした。集約とチャートの作業上限はスカラー演算300,000,000件と区分訪問100,000,000件。チャートの厳密値は65,536 bit、作業は262,144 bit、ピボットは512、一時行は768項、$L$ と $U$ の合計は65,000項を上限とした。個々のパッチ準備の設定は[ドライバー](pg-sparse-chart-series/run-series.cpp.txt)に固定した。

各標本の1回目のチャート準備を計時し、次に同じ原拘束を再構築した。因子の上限を最初の実項数に合わせると、同一のチャート識別子、rankと $L/U$ の項数で成功することを確認する。そこから1項だけ減らすと `ResourceExceeded` が返り、元の大域拘束を呼出し側が保持することを確認する。境界の再実行は表の準備時間に含めない。

## 再実行

WindowsのMSVC Releaseで、同じソースの `uvlas_structure` と `uvlas_core` をビルドする。リポジトリのルートで `$build` をそのMulti-Configビルド先に、`$deps` をvcpkgの `x64-windows` ディレクトリに設定する。次のコマンドを通す。

```powershell
$source = 'docs/verification/IM-01/pg-sparse-chart-series/run-series.cpp.txt'
$files = 'out/pg-sparse-chart-series'
New-Item -ItemType Directory -Force $files | Out-Null
pwsh tools/dev/msvc.ps1 cl /nologo /std:c++23preview /utf-8 /EHsc /TP /O2 /MD /W4 /WX /fp:strict /DNDEBUG /DNOMINMAX /Iinclude /Isrc/structure /Itests /Itests/structure "/external:I$deps/include" /external:W0 "/Fo$files/series.obj" $source "/Fe$files/series.exe" /link /STACK:67108864 "$build/Release/uvlas_structure.lib" "$build/Release/uvlas_core.lib" "$deps/lib/manual-link/Catch2Main.lib" "$deps/lib/Catch2.lib" /SUBSYSTEM:CONSOLE
if ($LASTEXITCODE) { throw 'Failed to link series' }

$runner = [System.Diagnostics.Process]::GetCurrentProcess()
$originalAffinity = $runner.ProcessorAffinity
$env:PATH = "$deps/bin;$env:PATH"
$cases = @('R02 two patches', 'R02 three patches', 'R02 four patch loop')
try {
    $runner.ProcessorAffinity = [IntPtr]4
    foreach ($round in 1..3) {
        for ($i = 0; $i -lt $cases.Count; $i++) {
            $log = Join-Path $files ("series-{0}-{1}.log" -f $round, ($i + 2))
            & "$files/series.exe" $cases[$i] --colour-mode none 2>&1 | Tee-Object $log
            if ($LASTEXITCODE) { throw "Failed case $($cases[$i])" }
        }
    }
} finally {
    $runner.ProcessorAffinity = $originalAffinity
}
```

各ケースを別プロセスで起動し、親から論理CPU 2のアフィニティを継承する。フェーズはパッチ準備、局所トレースと支持、大域原拘束、固定チャート。時刻は `steady_clock`、課金バイトは一つのResourcePlanの工程前後差。パッチ入力を組み立てる試験fixtureの別Planや、ドライバーの所有コンテナーは工程の課金に含まれない。OSの常駐量は各工程の終了時に採った。併記するピークはプロセス起動からその標本点までの最大値。

この系列では、因子保持項数の増え方が元CSR非零数の増え方と異なる。接続数、ループ、分割、物理順で列の結合が変わるため、R-02の実規模見積りには対象トポロジーごとの因子容量と準備時間が要る。ここで測ったのは静的な元拘束を渡す準備で、時間依存の右辺準備や時間積分全体、実務規模の性能認定は別の検証範囲とする。

## 同じ因子の再利用

同じ実パッチ系列を各1回、再利用モードで起動した。1回だけ準備したチャートで、固定支持を含む位置復元と転置を続けて1回ずつ呼んだ。独立座標 $r_{i,c}$ は $(i+2c+1)\bmod 9-4$、力 $f_{i,c}$ は $(i+2c+3)\bmod 9-4$。$i$ と成分 $c$ は0始まり。位置を元のCSRに戻した全行残差が零で、零でない仕事 $f^Tq$ が独立の有理積和による $(J^Tf)^Tr$ に一致した。大域拘束の再構築や分解を作用間に挟んでいない。

再利用の計時範囲は対象のAPI呼出し。作業用のCartesian三成分組は位置復元でrank個、転置で全座標組数と同数。返す座標と元行乗数の組数は作業用組数と分けてJSONに収録した。外部limbの見積りは製品の事前検査式で、局所の整数演算余裕と大域の生存有理数を含む。指定した作業幅による事前見積りとして、実測のRSSと課金から分けて記録した。
