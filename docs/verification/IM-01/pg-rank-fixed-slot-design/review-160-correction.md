# PR #160：入力と要求ケースの照合を訂正

2026-11-19。指摘 `discussion_r4623228782`、対象head `0f5c431d6d494b3907a08d9faa5d60728b73e302`。対象は容量probeの入力識別であり、製品の数値処理は変えない。

## 欠陥と再現

旧 `capacity-oracle.py.txt` は入力headerのgridと入力SHAから凍結行を探し、形状名を呼出側で後付けした。そのため、別の正常原本を誤ったファイル名へ置いても、その別ケースとして照合を通過した。

修正前に旧 `measure(path, "full", old_cases)` を同じ6原本で実行し、次を再現した。ここで要求ケースは旧mainがファイル名から付けるはずのケースを示す。

| 要求 | 渡した原本 | 旧measureの結果 |
|---|---|---|
| n1四次 | n1平坦 | 正常終了、grid1・244行 |
| n4四次 | n4平坦 | 正常終了、grid4・3,904行 |
| n1四次 | n4四次 | 正常終了、grid4・20,032行 |

この欠陥は取り違えを検出するという主張を損なう。旧12正常原本の容量値まで誤っていたとは判断せず、新版で独立に照合した。

## 訂正

旧producer・結果・検証記録・manifestはbyte保持した。訂正版 `capacity-oracle-v2.py.txt` は、呼出側が要求するn・形状・領域・行順の4キーで、まず凍結記録を一意に選ぶ。次に入力headerのn/F/N、最後にその一意な参照のSHAを検査する。参照の欠落・重複、入力の別grid・別shapeを、行列の容量計算前にValueErrorで拒否する。

同じ種類の誤りを新版全体で確認し、mainの12呼出しすべてで期待n/shapeを渡した。48 GiB比較に使うn4四次U形も、この照合を通過したケースからだけ選ぶ。凍結結果を入力側の自己申告で逆選択しない規則を `reference-data.mdc` に追記した。

## 対象検証

Windows、Python 3.12標準ライブラリで新版だけを実行した。

```text
python -B capacity-oracle-v2.py.txt --inputs <6原本directory> --study <凍結studyのresults.json> --output <新規出力>
```

- 正常12件を再発行し、旧結果の全case値・既存729恒等式/4反例・同時保持比較の各JSON値と完全一致した。
- 同nのshape交換4通り、同shapeのn交換2通り、n/shape双方の交換1通りを、全背景とU形の両方へ適用した14負例をすべて拒否した。入力自体は凍結した別ケースの正しい原本であり、SHA破損だけの試験ではない。
- 正しい原本でも、期待する凍結行が欠落または重複する2負例を拒否した。
- 新版結果SHA-256は `d1ca719d7677601e5f7e86f857c0ecb44301c5f0daa5d1582bd7c4e84d1c76af`。

今回の変更は実験の識別条件だけであり、容量式・数値値・許容差・48 GiB要求は不変である。全rankや製品C++の再ビルド、取消・例外・並列の試験は影響がないため重ねない。固定arenaでの全call実行と製品開始の認定は、引き続きIM01-7/#140に残る。新規証拠の整合と追跡を確認し、inline threadは利用者の確認まで開いたままにする。
