# 固定整数化から共有リフトへの引き渡し

四次n4の全背景とU形切断で、固定整数化が作ったCSCの整数係数と列境界を共有リフトに引き渡した。
両方の配列について引き渡しの前後で先頭アドレスが一致した。
各領域の1,496候補で独立証明書との厳密照合に通り、列別診断のSHA-256も従来の共有リフトと一致した。
IM01-7の子Issue #250の検証記録である。

## 整数係数と行尺度を渡す

容量の上限は従来と同じ48 GiBとし、固定整数化は従来の1,536ビットの領域を使う。
先に全行の尺度とCSCを独立な動的厳密算術と照合し、係数幅と尺度幅の最大値も比較する。
次に行整数化の配列を同じ型のままリフトの入力へ移し、選択列と証明書用の座標表を取得する。
共有ブロックを組み立てるときだけ、整数化で求めた全行尺度を借りる。
ピボット行の尺度は直接有限体へ落とし、行尺度、行の印、整数化の一時領域はバッチに入る前に解放する。

| 量 | 全背景 | U形切断 |
|---|---:|---:|
| CSCの整数係数数 | 2,146,784 | 524,715 |
| CSCの列境界数 | 1,497 | 1,497 |
| 最大の行尺度幅 / 整数係数幅（ビット） | 110 / 127 | 110 / 124 |
| 全候補の証明行数 | 29,967,872 | 8,428,464 |
| 独立証明書との座標照合数 | 1,157,904 | 745,008 |
| 右辺の読み取り対象になった整数係数数 | 951,340 | 231,163 |

独立証明書の選択列・候補番号・元式・座標と、既存の共有リフトの列別診断・集計値を照合した。
最初の従属候補と全候補を別プロセスで試し、全背景の列別診断は `2e13d29c1e729d6fa79173948b38b4c10e773c3aa84e736acf102c52a996b78c`、U形切断は `ac25bce5f466c4f9f9f0ea502bf22aa1c8c9710250ac0df639de6e4a78a58d8b` だった。
固定整数化の算術と、共有右辺の読み取りから全行証明までのバッチで、監査対象の追加確保試行は両領域とも0件だった。

## 固定領域の容量

| 同時に保持する範囲（B） | 全背景 | U形切断 |
|---|---:|---:|
| 固定整数化の事前算定と実測容量（両者は一致） | 450,631,648 | 110,304,104 |
| 選択列と証明書座標表を含む事前算定 | 2,840,548,744 | 1,648,002,752 |
| 共有ブロック構築後の固定領域 | 2,844,565,360 | 1,650,157,944 |
| バッチ前に解放する整数化専用領域 | 4,088,600 | 1,151,408 |
| バッチの固定保持容量 | 2,864,629,064 | 1,657,138,696 |
| 従来のバッチの固定保持容量 | 2,909,437,240 | 1,693,580,696 |

選択列と証明書座標表を確保する前に、整数化の実容量、入力の所有オブジェクト、選択列配列、全候補の座標表を合算して上限を確かめた。
確保後も容量を再集計して事前値と一致することを確認した。
共有ブロックは構築後に計上したため、表の容量には構築中の一時領域が含まれない。
バッチの固定保持容量にはリフトの作業領域も入る。
整数化段階とバッチ段階の表の値は、最初の候補と全候補でそれぞれ一致した。

ランナーは独立に算出した事前値、旧版の共有ブロック容量、旧版の固定保持容量からCSCの余剰容量を引いた値と比較する。
MSVCでの入力所有型は144 B、座標ペアは2,064 B、整数係数は208 B、列境界は8 Bであることをコンパイル時検査で確かめた。
段階的に追加する旧版の配列容量はMSVCの成長式を使って算出した。
固定保持の差は、両領域とも、今回配列を必要数で一度に確保したことによるCSCの余剰分と一致した。

実行前に利用可能な物理メモリ19,598,585,856 Bとコミット余裕10,783,236,096 Bを確認した。
直前までの固定整数化の単独実行をもとに設けた目安6,268,223,488 Bを両方が上回ったため、各プロセスを順に実行した。
動的行列の展開、有限体因子、動的な厳密参照、証明書の読み込みと共有ブロックの組み立てには監査外の確保がある。
[実行結果](result.json)のプロセスピークと区間時間は、この環境での観測値である。
準備全体の事前容量保証と製品規模での性能評価はIM01-7に残る。

## 再現

1. [整数化の記録](../pg-rank-fixed-row-integerization/verification.md)と[共有リフトの記録](../pg-rank-shared-fixed-batch/verification.md)に従って凍結係数・全背景とU形切断の証明書を用意する。領域ごとに疎な行順の証明書を使う。
2. `python -B compose.py.txt --help` にある引数へ[合成記録](composition.json)の6ソースと `row-handoff.hpp.txt` を渡し、別の場所に翻訳単位と合成記録を生成する。共有リフトと同じMSVC 19.51.36260、Boost 1.92.0、`/std:c++latest /O2 /EHsc /MD /DNOMINMAX`、スタック予約64 MiBでコンパイルする。固定バッチのディレクトリもインクルードパスに加える。合成ソースと実行ファイルのSHA-256は別々に保存した。
3. `python -B run-connected.py.txt --help` にある引数へ凍結入力・証明書、索引、容量調査、合成記録、実行ファイル、固定整数化の `review-243-result.json`、共有リフトの `results.json`、各検査ランナーを渡す。先にネイティブの3組の対照を通し、領域ごとに最初の候補、全候補の順に実行する。各ネイティブプロセスの上限は60秒で、両領域が成功してから結果を公開する。
4. `python -B gate-probe.py.txt` と `python -B -O gate-probe.py.txt` にリポジトリルート、凍結係数、両証明書、実行結果を渡す。記録済みの集計を使うゲートで、合成3件、出力公開14件、入力の直接指定とハードリンク28件を検査し、両モードが同じ[結果](gate-result.json)になった。公開検査では既存の出力がある場合もない場合も、後段の失敗、CSC再確保の報告、係数幅、事前容量と共有領域込みの容量の同時改変、固定保持容量、列診断ハッシュの改変を拒み、従来の出力状態を保った。
