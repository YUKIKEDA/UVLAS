# n4平坦・四次の全背景で全候補を厳密に再構成した

固定領域の再構成をn4の平坦・四次の全背景に適用し、全候補について元式の全活動行と独立証明書の全座標が一致した。元の候補順と資源上限を使い、監査中の追加確保試行は両形状で0件だった。IM01-7の子Issue #214の検証記録である。

| 観測 | 平坦 | 四次 |
|---|---:|---:|
| 活動行 | 3,904 | 20,032 |
| 候補（選択／従属） | 1,237（490／747） | 1,496（774／722） |
| 元式の厳密な零残差照合 | 4,829,248 | 29,967,872 |
| 独立証明書との厳密な座標照合 | 606,130 | 1,157,904 |
| 定義イベント | 25,002,015 | 1,294,268,522 |
| 固定保持容量 B（計画と実容量が一致） | 2,360,203,696 | 6,925,475,920 |
| 復元座標の最大ビット幅 | 32 | 1,809 |
| 元式の証明に使う中間値の事前幅上界 bit | 91 | 2,014 |
| 監査時間 ms | 282 | 11,038 |
| プロセスのピーク常駐量 B | 2,371,944,448 | 7,139,323,904 |

観測値の出典は [平坦の結果](flat-result.json) と [四次の結果](quartic-result.json)。四次では72従属列が128桁を使った。各起動は60秒以内で完了し、従来の8,192 bit、128桁、定義イベント20億、固定保持48 GiBの上限に収まった。時間と常駐量は並行負荷下の単回観測である。

## 係数と証明書を固定して再現する

1. 凍結した係数原本と証明書を用意する。ランナーは `n=4`、要求した形状、`full`、`sparse` で記録を一意に選ぶ。係数と証明書のヘッダー・SHA-256を照合し、有限体で選んだ全基底列とピボット行を証明書に照らす。
2. `derive-driver.py.txt --base <固定C++核> --shared-producer <n2派生器> --output <生成先.cpp> --record <来歴.json>` を `python -B` で実行する。生成元をSHA-256で固定し、`main` のn条件と診断だけを変更する。逆変換では元の全バイトが一致した。
3. Windows x64で、MSVC 19.51.36260とBoost 1.92.0を使って生成先をビルドした。オプションは `/TP /std:c++latest /O2 /EHsc /MD /DNOMINMAX` と `/STACK:67108864`。Boostと元の固定C++核を置くディレクトリをインクルード先に加えた。limb幅は32 bit。
4. `run-case.py.txt` に `--shape <flat または quartic>` と、係数・証明書の各ディレクトリ、バッチ実行ファイル、共通ランナー、n4切断ランナー、容量検査器、調査記録、証明書索引、生成来歴、別の出力先を渡す。共通対照、最初の従属列、全候補の順に検査する。出力先と入力ファイルの衝突は起動前に拒否する。

生成C++のSHA-256は来歴に、実際に起動したバイナリのSHA-256は結果に記録した。保存結果には、選択列、桁分布、幅、全列診断をキー順固定かつ空白なしのJSONにしたときのSHA-256も含めた。列診断を再生成するには、同じバイナリへ同じ係数・証明書と `all` を直接渡して標準出力を捕捉する。

## 四次の全実行前にホストのメモリ余裕を確認した

四次の最初の従属列を別プロセスで実行し、ピーク常駐量3,143,213,056 Bを観測した。全実行ではそこから721列分の準備データが増える。[先行の四次全背景1列](../pg-rank-fixed-lift/results.json)の固定保持8,841,232 Bはスクラッチも含むため、複製1件の固定容量の上界として用いた。行スケールは非零項を保ち、ピボット部分行列と因子の格納サイズは各対象列で等しい。

増分6,374,528,272 Bを初回ピークに加えた目安の2倍を、実行前の余裕確認に使った。四次の起動直前に物理メモリ空き28,151,607,296 Bとコミット余裕25,883,074,560 Bを得て、いずれも目安の19,035,482,656 Bを超えた。これは同じホストでの実行判断に用いた見積もりであり、プロセス常駐量や準備資源の保証式ではない。

## 不完全な確認結果や入力との衝突では公開しない

実計算と別に、平坦の集計と基底列から作った列診断のスタブで公開ゲートを検査した。通常モードと `python -O` のそれぞれで、旧出力あり・なしの20件と、9入力に対する直接・ハードリンクの18衝突を確認した。行・座標不足、列診断異常、別形状の入力、来歴不一致、タイムアウト、置換失敗で公開を中止し、入力と既存出力のバイト列を保持した。派生器でもハードリンク衝突と原本の変異を拒否した。[ゲートの結果](gate-result.json)

監査の範囲は復元と証明のバッチである。実験用の動的な入力・行列・因子・行スケールの準備は監査外で、定義イベントは全call・全limb操作の上界を与えない。共有準備、辞書・分割との同時容量、未実証のケース、製品開始の判定は親Issue #140で扱う。
