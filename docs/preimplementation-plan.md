## 4. 最初に作る問題定義

最初に、以下を満たす「連成系全体の数学的な問題定義」を作る。単体要素の選定だけから開始しない。

1. 参照配置、現在配置、慣性系・材料系、構造領域・空力面・後流・支持・外力を図と記号で特定する。
2. 独立変数、未知量、パラメータ、履歴、拘束、既知入力、観測量を分ける。集中質量・梁・積層・非一致格子も含める。
3. 理論式の成立条件と、製品要求の各機能がどの項に対応するかを記載する。
4. 静的平衡、過渡応答、平衡周りの安定性について、同じモデルから何を固定・除去・線形化して問題を作るかを示す。
5. 空力面と構造表面の位置・速度・荷重・仕事の対応、時間依存入力が系へ仕事をする経路を示す。

例えば構造方程式を記号的に書くなら、

$$
R_{s} = M(q) a + h(q,v) + f_{\mathrm{int}}(q) + f_{\mathrm{damp}}(q,v) + C_{q}^{\mathsf T} \lambda - Q_{\mathrm{ext}}(q,v,\gamma,w,t) = 0
$$

$$
C(q,t) = 0
$$

という形で、慣性の構成依存性、拘束、空力・写像の荷重依存性を落とさずに整理する。ただし、この記号式を書くだけでは完了しない。採用要素についてM、h、 $\mathbf f_{int}$ 、C、 $\mathbf Q_{ext}$ を定義し、不要になる項とその根拠を示す。空力・後流・写像も同じ記号系で定義する。

## 5. 各方式の採用記録

方式・ライブラリごとに、次を一つの設計決定として記録する。

- 対応要求、解決する問題、利用条件と対象外。
- 候補、原資料の版・式・該当箇所、自作／既存実装利用／参照のみの区別。
- 具体的な採用式と導出・変更点。論文名や既存クラス名だけでは選定を閉じない。
- 精度、保存特性、ロッキング・特異性、収束性、接続性、計算量・メモリ、依存・配布条件の比較。
- 採用理由、棄却理由、確認した証拠、未確認事項と影響する要求。
- 必要な実験・照合、決定の状態、再検討の条件。

状態は「未着手／調査中／比較・根拠作成中／選定済み／基準化済み／要再検討」で管理する。候補を挙げただけで選定済みとしない。選定済みとした後も、式・契約・ケースへの反映と整合確認が済むまでは基準化済みにしない。

開始審査に合格する前は計算本体のコードを追加しない。現在IM-00は合格し、その範囲から着手可能。検証スクリプトや技術試作が方式選定に必要な場合は、先に「検証したい仮説、候補、入力、独立した比較対象、観測量、合否・採否基準、打切り条件、結果の使い方」を文書化する。

## 8. 計算本体の実装開始条件

2026-11-04の適用整理：以下は**当該パッケージの式・契約・不変条件と検証方法を固定する条件**であり、全製品の検証結果をPython試作で先に揃える条件ではない。方式を棄却する決定的な試験や、採用を左右する技術試作は実装前に必要。一方、仕様を固定した部品の全ケース・全材料組合せの網羅、製品規模の実測、実務受入の完了は実装と対応させる。実装後へ残す検証の入力・参照・許容差・未達時の扱いは先に定める。残る未決定が当該処理の式やI/Fを変える場合は、その処理の開始を保留する。現MMS-1の不採用は維持し、主シェル問題を他領域へ先送りしない。

各パッケージについて次を全て満たし、開始判定記録を残す。

1. 連成系全体の問題定義と、当該処理が占める位置・責任が確定している。
2. 当該処理と接続先の採用式、離散未知量、符号・単位・時刻・境界初期条件に、実装者の推測を必要とする未決定事項がない。
3. 入出力の型・形状・配置・所有権・変更範囲・失敗時の保証が定義されている。
4. 主要処理の擬似コードと状態遷移、関連する接線・履歴・キャッシュの条件が定義されている。
5. 不変条件、確認ケース、具体的な入力、独立参照または構成法、誤差指標、事前許容差が揃っている。
6. 必要な数値依存・線形系の性質・容量見積もりに致命的な未解決事項がなく、必要な限定試作が済んでいる。
7. 要求→式→契約→処理→不変条件→ケースの対応が追跡でき、相互矛盾がない。
8. 残る懸案が当該パッケージを変更しないと説明できるか、影響範囲ごとに実装を保留している。

全製品の細部を一度に確定することは求めない。ただし、共通の問題定義と接続境界を閉じずに、単体カーネルから既成事実を積み上げる進め方は採らない。最初の実装パッケージは、系全体の定義後に最も小さく閉じられる対象を選び、決定台帳から依存閉包を作って判定する。

公開実験による全機能の妥当性確認結果は製品受入までに必要な証拠であり、コード実装前に結果が存在することは求めない。一方、実装前にその計画、必要なデータ、取得見通し、不足時の扱いを定義する。初期の必須部品ケースに独立参照がないまま実装へ進めない。

## 9. 役割とレビュー

製品目的・対応範囲・精度・性能・運用の変更はユーザー判断事項。既決のQ1〜Q27は維持する。アシスタントは原資料調査、導出、候補比較、技術採用案、契約・ケース仕様、整合点検を進め、用途・品質・工数の選択が必要になったときだけ根拠付きでGrillする。独立した質問は本文でまとめる。

アシスタントによる自己点検を人的な独立レビューと記載しない。公開文献・独立コード・解析解による照合と、誰が設計をレビューしたかを区別して記録する。独立レビューが未実施ならその状態を明記する。ユーザーへ全ての細かな技術判断を投げたり、文書を読んだことだけで承認済みとしたりしない。
